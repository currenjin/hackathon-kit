# 사전 준비 완료 기준

이 기준은 kit의 작업 완료 기준이지 공식 행사 규칙이나 수상 보장이 아니다. 목표는 **현장에서 제품을 다시 기획하지 않고, 합의한 설계를 구현하고 검증하는 데 바로 들어가는 상태**다.

[workflow 계약](workflow-policy.md)의 행위별 허용과 사용자 승인 안에서만 준비한다. 코드 금지를 기획 전체의 금지로 확대하지 않고, 기획 허용을 design/prompt/data/criteria 허용으로 확대하지 않는다.

## 세 가지 필수 산출물

별도 파일 수나 새 YAML schema를 강제하지 않는다. 기존 `ideation.md`, `design.md`, `preparation.md` 또는 연결된 명세·실행계획을 쓰고, `/preflight pre-event` 보고서에 현재 버전과 해당 절을 연결한다. 파일 존재나 체크 표시만으로 통과시키지 않는다.

### 1. 제품 명세

`/ideate`에서 방향을 선택한 뒤, `/design`에서 화면을 정하기 전에 빈칸을 확인한다.

- 누가 어떤 상황에서 어떤 일을 끝내려는가. 중요한 문제라는 근거와 아직 가설인 부분은 무엇인가.
- 구체적인 입력 형식과 허용 범위, 사용자의 실제 행동, 최종 산출물은 무엇인가.
- 이번에 지원하는 업무와 제외하는 업무는 무엇인가.
- 무엇이 고정된 화면·기능이고 무엇이 입력에 따라 달라지는가. 문구만 바뀌는 데모를 동작 생성으로 설명하지 않는다.
- AI, 결정론적 코드, 사람의 검토·승인이 각각 무엇을 맡는가.
- 어떤 결과를 성공, 실패, 확인 필요로 볼 것인가. 제품·모델 출력으로 성공 기준을 역산하지 않는다.

방향 선택이나 제품명 확정만으로 명세 완료가 되지 않는다. 사용자가 채택하지 않은 예제 업무를 확정 범위로 밀어 넣지 않는다.

### 2. 화면·상태 설계와 사용자 검토

`/design`은 허용된 문서·와이어프레임·이미지·스토리보드 등으로 처음부터 끝까지 같은 제품을 상상할 수 있게 만든다. 코드 없는 설계가 필요한 행사에서 HTML 목업이나 제품 코드를 필수로 요구하지 않는다. 비코드 산출물도 각각의 공식 허용 범위를 확인한다.

CLI·API·파일 제품은 해당 입출력 surface와 상태 변화로 같은 흐름을 명시한다. 준비 기준을 맞추려고 범위에 없던 웹 UI를 추가하지 않는다.

- 최초 진입과 입력: 무엇을 넣고 무엇을 기대하는지 보여준다.
- 처리 준비와 업무 맥락: 사용자의 역할, 목표, 현재 상황을 설명한다.
- 실제 조작: 누를 버튼·입력할 값과 동작 가능한 조건을 구체화한다.
- 상태 전이: 동작 후 어떤 데이터·업무 상태·결과·안내가 바뀌는지 연결한다.
- 완료: 무엇을 끝냈고 무엇을 확인하거나 가져갈 수 있는지 보여준다.
- 예외: loading, 잘못된 입력, 빈 결과, 문서 정보의 누락·모순, 모델·인프라 실패와 복구를 필요한 범위에서 정한다.

튜토리얼·도움말이 있다면 단순 클릭과 업무 완료를 구분한다. 안내는 실제 입력·처리 결과·상태를 기다려 진행하고, 로딩·오류·대상 미등장 시에도 현재 상태와 일치해야 한다.

사용자에게 검토할 산출물을 실제 전달하고, 검토한 버전·승인 여부·미해결 쟁점을 기록한다. 방향이나 레퍼런스에 대한 동의는 화면·상태 설계 승인으로 대체하지 않는다. 필요한 검토가 대기 중이면 미완료다.

### 3. 현장 실행 계획

`/prepare`의 작업계획 또는 연결된 runbook에 적고 `/preflight pre-event`에서 확인한다. `/prepare`의 제품 구현 입력이 아직 없으면 준비 점검을 위해 구현 command를 강행하지 않는다. 기존 허용 계획 문서에 정리할 수 있으며 preflight에 `/prepare` 실행을 필수로 요구하지 않는다.

- 공식 제작 시간과 마감 안에 계정 설정, 가장 위험한 모델/API 확인, 첫 E2E, 조기 배포, 품질 검증, 발표·영상 등 해당 행사의 산출물과 제출·백업을 어떤 순서와 시간 예산으로 끝낼 것인가.
- 최우선 가설을 어떤 최소 입력과 독립 성공/실패 기준으로 확인할 것인가. `/demo criteria`는 허용된 시점에 제품 구현·실제 출력 판정 전에 고정한다.
- 정상 입력과 잘못되거나 모호한 입력에서 무엇을 기대하고, 언제 진행·질문·중단할 것인가.
- 시간·모델 품질·권한·배포가 부족하면 어떤 조건에서 무엇부터 축소할 것인가. 축소 후에도 핵심 사용자 가치와 필수 자격을 유지할 수 있는가.
- 새 기획 없이 시작할 첫 작업, 실행·reset·재현 방법, 행사에서 요구하는 언어·형식의 산출물과 접근 조건 확인 순서는 무엇인가.

예산은 해당 행사의 실제 제작 시간에 맞춘다. 코딩만 예산에 넣거나 모든 API 실패를 고정 응답으로 숨겨 해결하지 않는다. 계정 생성, 유료 호출, 공개 전환, 배포와 실제 제출의 별도 승인 경계를 유지한다.

## walkthrough 완료 판정

허용된 산출물을 보며 **입력 → 사용자 행동 → 화면·상태 변화 → 결과 → 예외와 복구**를 처음부터 끝까지 따라간다. 수행자·일시·검토 버전·발견한 빈칸과 해소 여부를 기록한다. 사용자 설계 검토와 이 설계 walkthrough는 실제 제품 실행·사람의 발표 리허설과 다르다.

다음 질문이 제품의 핵심 결정으로 남아 있으면 사전 준비 미완료다.

- 여기서 무엇을 보여주고, 사용자가 무엇을 하는가?
- 이 버튼을 누르면 어떤 상태와 결과가 되는가?
- 이 부분은 AI가 만드는가, 고정 코드인가, 사람이 정하는가?
- 입력이 부족하거나 결과가 잘못되면 어떻게 되는가?

미세 색상, 전체 코드 구조, 모든 주변 기능까지 미리 확정할 필요는 없다. 제품 정체성·핵심 경험·성공 판정을 바꾸는 결정을 현장에 넘기지 않는다.

## 현장에서만 가능한 확인

지급 전 계정·권한·quota, 실제 모델의 가용성·품질·응답시간, 실배포는 미확인으로 남겨도 된다. 각 항목에 아래를 모두 적으면 **현장 확인 대기**로 분리하며, 불가능한 사전 실호출을 준비 완료의 필수 조건으로 만들지 않는다.

- 사전에 확인할 수 없는 이유
- 언제 어떤 경로와 최소 입력으로 확인할지
- 독립 성공/실패 기준
- 실패 시 대체 경로와 허용·자격 영향
- 중단 또는 범위 축소 조건

핵심 제품 설계의 빈칸이나 사용자 검토 미완료를 계정 미지급 탓의 현장 확인 대기로 돌리지 않는다. 사전에 확인 가능한데 하지 않은 항목도 이 예외에 넣지 않는다. 사전 criteria 자체가 금지·미확인이면 지금은 허용된 확인 절차만 계획하고, 금지된 expected·fixture·prompt 작성을 강요하지 않는다.

## 보고와 최종 판정

다음 상태를 근거 경로와 함께 별도로 보고한다.

- **제품 계획 준비:** 제품 명세, 화면·상태 설계, 사용자 검토와 walkthrough, 현장 실행 계획의 완료·미완료.
- **실행환경 준비:** 지참 기기·범용 스타터·도구의 실제 검증 범위. 준비 호스트와 현장 기기, SDK import와 실제 추론, 일반 샘플과 제품 검증을 구분한다.
- **현장 확인 대기:** 위 조건을 갖춘 계정·모델·권한·배포 확인과 대응 계획.
- **실제 제품 검증:** 미구현·미실행 또는 실제 제품 경로와 독립 기준으로 확인한 결과. 사전 구현 허용 행사에는 기존 E2E·UI·복구 완료 기준도 적용한다.

스타터 준비, 의존성 설치, 압축팩, checksum, build PASS는 실행환경 준비의 증거일 뿐이다. 세 산출물이나 핵심 결정이 미완료면 전체 결론은 **사전 준비 미완료**이며, 가장 먼저 해결할 빈칸과 담당 command를 적는다.

세 산출물과 검토가 충족되고 사전에 확인 가능한 준비를 검증했으며 외부 의존 확인에 대응 계획이 있으면 **사전 준비 완료 · 제품 미구현/현장 확인 대기**처럼 범위를 한정한다. 이는 제품 PASS, 발표 준비 완료, 제출 완료가 아니다.

공식 금지·허용 미확인 때문에 필요한 기획·설계를 수행할 수 없으면 **공식 제한으로 준비 범위만 점검**이라고 보고한다. 해당 항목을 N/A로 지워 전체 준비 완료로 승격하지 않는다. 금지된 코드·prompt·fixture를 만들어 기준을 채우지 않는다.
