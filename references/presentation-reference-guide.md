이 문서는 신규 deck에 적용할 추천 흐름이다. 기존 deck을 자동 재생성하거나 행사 workspace를 일괄 migration하지 않는다. 공식 행사 규칙과 [AGENTS.md](../AGENTS.md)의 발표시간·독립 evidence 계약이 우선한다.

## 투자 피치: 전달 방식만 선별한다

1. [Kevin Hale / YC](https://www.ycombinator.com/blog/how-to-design-a-better-pitch-deck/)에서 배울 점은 읽을 수 있는 크기·대비, 한 장의 한 메시지, 즉시 드러나는 결론이다. 1분에는 문제 한 문장과 핵심 결과를 큰 화면으로 전달한다. 그대로 옮기면 안 되는 조건: 원문은 투자자 대상 Demo Day이며 당시 150초와 5~7장 맥락이다. 원문의 screenshot·영상 회피 의견을 해커톤의 실제 working demo 삭제 근거로 쓰지 않는다. UI를 크게 잘라 보여주되 결과를 조작하지 않는다. before/after 이미지는 미열람, 설명 텍스트만 확인했다.

2. [Dominika Blackappl / YC](https://www.ycombinator.com/blog/practical-design-pitching/)에서 배울 점은 기억에 남길 사실부터 고르고 발화와 슬라이드의 역할을 나누는 것이다. 원문도 순서 변경·일부 생략을 허용한다. 1분에는 검증된 핵심 변화와 차별점만 선택한다. 그대로 옮기면 안 되는 조건: 투자 후속 미팅을 위한 150초 도구다. 시장규모·성장·팀을 포함한 전체 9항목을 60초 해커톤에 강제하지 않는다. 미확인 고객·매출·시장 수치를 만들지 않는다.

## 일반 발표 설계: 대본과 청중 이해를 먼저 둔다

3. [Team Duarte](https://www.duarte.com/blog/make-a-presentation/)에서 배울 점은 대본을 먼저 쓰고, 하나의 중심 메시지를 정하고, 시각 제작 전에 구조를 다른 사람에게 검토받는 순서다. 1분에는 현재 문제에서 실제 해결 결과로 이어지는 짧은 발화 초안을 먼저 잡는다. 그대로 옮기면 안 되는 조건: 일반 발표 설계의 persona·여정 작업을 모두 발표 슬라이드로 내보낼 필요는 없다. 긴 감정 곡선이나 모든 단계의 별도 장수를 강제하지 않는다. 영상은 미시청이다.

4. [Kevin Friesen / Duarte](https://www.duarte.com/blog/how-to-write-a-great-presentation/)에서 배울 점은 청중이 무엇을 이해해야 하는지 정하고 시작·중간·끝을 연결하며, 한 장에서 불필요한 정보를 덜어내는 것이다. 1분에는 배경 지식 없이 문제와 결과를 이해할 수 있는지 확인한다. 그대로 옮기면 안 되는 조건: 설득 프레임은 증거를 대체하지 않는다. 근거 없는 미래 효과를 현재 성과로 표현하거나 긴 도입·CTA로 데모 시간을 잠식하지 않는다. 내장 영상은 미시청이다.

## TED/TEDx: 무대 가독성과 리허설을 가져온다

5. [TEDx 운영 가이드](https://www.ted.com/tedx/organizer-guide/prepare-speakers-and-program)에서 배울 점은 슬라이드의 필요성을 먼저 판단하고, 한 장에 한 요점만 두며, 먼 좌석에서도 읽히는지 실제 환경에 가까운 리허설로 점검하는 것이다. 1분에는 핵심 화면과 전환 cue를 포함해 연습한다. 그대로 옮기면 안 되는 조건: TED 강연·행사 운영 규칙은 해커톤의 발표시간·심사 기준이 아니다. 무슬라이드 권장이나 강연 구성을 working demo 생략 근거로 쓰지 않는다. 이미지 사용 권한은 별도로 확인한다.

## 해커톤: 실제 제품 동작을 중심에 둔다

6. [Brandon Kessler / Devpost](https://info.devpost.com/blog/how-to-present-a-successful-hackathon-demo)에서 배울 점은 짧은 문제 설명 뒤 작동하는 제품을 보여주고, 처음 제기한 문제의 해결 결과까지 도달하는 것이다. 1분에는 불필요한 로그인·계정 생성·타이핑을 미리 준비해 핵심 조작과 전후 변화에 시간을 쓴다. 그대로 옮기면 안 되는 조건: 인증 자체가 핵심 기능이면 무조건 생략하지 않는다. 미래 가능성은 현재 구현과 구분한다. 녹화·mock을 live 성공으로 말하지 않는다.

7. [Stephanie Rochon / Devpost](https://info.devpost.com/blog/6-tips-for-making-a-hackathon-demo-video)에서 배울 점은 대본을 구간별 초수로 나누고 실제 사용 모습을 보여주며 녹화·업로드 시간을 확보하는 것이다. 1분에는 핵심 결과를 앞쪽에 두고 말이 넘치면 정보를 줄인다. 그대로 옮기면 안 되는 조건: 참가자 경험을 모은 글이지 수상 인과 연구가 아니다. 제목의 winning이나 참가자의 수상 횟수를 우승 보장으로 해석하지 않는다. 약 3분이라는 사례보다 해당 행사의 공식 영상 길이를 우선하며 영상 편집을 live 실행 evidence로 대신하지 않는다.

8. [Devpost Help Center](https://help.devpost.com/article/84-video-making-best-practices)에서 배울 점은 홍보 영상보다 실제 화면과 음성 설명으로 기능을 보여주고, 초반에 제품을 설명하며 대본·리허설을 준비하는 것이다. 1분에는 실제 입력→조작→결과를 보여주는 짧은 screencast를 fallback 후보로 둔다. 그대로 옮기면 안 되는 조건: 편집 허용 조언은 제품 실패나 대기시간을 숨겨 실제 성능으로 주장할 허가가 아니다. 영상 속도·편집 여부를 구분하며 행사 규칙을 확인한다. 하단 자격 안내 이미지는 미검증이므로 그 내용은 인용하지 않는다.

## 1분 기본안: 사용자 정책에 따른 우리의 제안

명료함·가독성·한 장 한 메시지는 [1]·[4]·[5], 대본 우선은 [3]·[7]·[8], 작동 데모와 불필요한 로그인 생략은 [6], 시간 분배·리허설은 [5]·[7]·[8]에서 각각 가져왔다. 모든 출처가 동일한 규칙을 말한 것은 아니다. 이 조합은 전달 개선을 위한 제안이지 우승 원인·확률·보장이 아니다.

아래 시간 배분과 대표 렌더 승인 절차는 사용자 정책에 따른 kit 제안이다. 어느 출처의 공식 60초 정답도 아니다.

| 구간 | 초 | 역할 |
| --- | ---: | --- |
| 문제 | 8 | 누가 어떤 불편을 겪는지 한 문장 |
| 핵심 변화 / 데모 | 32 | 실제 입력·핵심 조작·전후 결과, 동시 발화 포함 |
| 차별 / 기술 | 12 | 왜 이 방식인지, 검증된 차별 한 가지 |
| 마무리 | 3 | 기억할 가치 한 문장 |

| 합계 | 60 | 8 + 32 + 12 + 3 + 5, 프로그램으로 계산 확인 |

발화와 데모가 동시 진행되는 구간은 두 번 더하지 않는다. 총 경과시간에는 loading·전환·여유를 포함한다. 장수 기본값은 두지 않고 시간 안에 필요한 메시지·실제 핵심 데모·가독성과 공식 제출 조건으로 장수를 정한다. 장수를 채우려고 내용을 만들지 않는다. Q&A가 포함된 공식 슬롯이라면 Q&A 예산도 그 안에 두고 발표 구간을 다시 나눈다. Q&A 조건이 미확인이면 별도라고 가정하지 않고 최종 준비에는 RISK를 남긴다.

## 시간의 단일 기준과 변경 계약

[템플릿](../templates/hackathon.yaml)의 기존 `event.pitch_minutes`는 공식 안내 시간만 기록한다. 공식 미확인은 `null`로 유지한다. 초 단위 안내도 분으로 정확히 환산해 보존한다. Q&A 조건은 `presentation.qa_mode`에 `unknown | included | separate | none`으로 기록한다. 공식 또는 사용자 확인으로 Q&A가 없으면 `none`, `qa_seconds: 0`이다. 그 외 `qa_seconds`는 확인된 배정만 쓰고 미확인은 `null`이다. 원문 표현·확인일·시간 범위·Q&A 출처는 기존 `notes`에 남기며 official/user-confirmed를 구분한다. Q&A의 사용자 확인은 공식 발표시간이나 규칙 확인을 뜻하지 않는다. 새 템플릿은 `unknown`/`null`을 유지하며 다른 행사까지 없음으로 가정하지 않는다.

공통 해석 규칙:

- `event.pitch_minutes`가 유효한 양수이고 공식 근거가 확인되면 `effective_seconds = pitch_minutes × 60`, `timing_status = official`, `source = 공식 URL/운영진 안내 식별자`다. 공식 180초를 60초로 덮어쓰지 않는다.
- 공식값이 없고 출처 있는 사용자 확인 시간도 없으면 `event.pitch_minutes = null`, `effective_seconds = 60`, `timing_status = provisional`, `source = user-default`다. 이는 발표·데모·전환을 합친 준비용 예산이며 공식 확정이 아니다.
- 사용자가 시간이나 범위를 확인하면 공식값은 null로 유지하면서 `timing_status: user-confirmed` 또는 `user_confirmed_range`, 원문 source와 준비 목표 effective_seconds를 기록한다. 범위가 있으면 선택 필드 allowed_range_seconds 또는 기존 notes에 남기고 목표가 범위 안인지 대조한다. 사용자 확인3–4분에 목표210초를 선택한 경우 기본60초로 덮지 않는다. 새 공식 안내가 오면 우선 적용하되 충돌은 확인하고 영향받은 자료는 dirty로 둔다.
- 기존 행사에서 필드가 없으면 같은 해석을 읽기 시 적용한다. 기존 공식값의 출처를 찾지 못하면 그 값은 보존하고 출처 확인 대기로 둔다. 임의로 60초로 덮거나 공식 확인으로 승격하지 않는다. 0·음수·문자열 오류도 기본값으로 숨기지 않고 확인한다.
- `effective_seconds`는 공식값의 환산 또는 출처 있는 사용자 확인 범위 안에서 선택한 준비 목표이지 근거 없는 override가 아니다. 공식값과 불일치하면 제작을 멈추고 정합성을 먼저 해결한다. `/deck`과 `/pitch`는 시간·출처·Q&A 조건을 동일하게 기록한다.
- `qa_mode = included`이면 유효시간은 Q&A까지 포함한 슬롯이다. 알려진 `qa_seconds`를 먼저 배정한다. 포함 여부나 배정이 미확인이면 최종 발표용 예산을 확정했다고 하지 않는다. Q&A를 임의로 0초/별도로 처리하지 않는다.
- `qa_mode = none`은 공식 또는 사용자 확인 근거가 있을 때만 쓰고 `qa_seconds = 0`이어야 한다. 이때 Q&A 대본·시간 배정은 필수가 아니며 Q&A 답변 검수는 근거와 함께 N/A로 기록한다. unknown을 none으로 간주하지 않는다. 공식 안내와 사용자 확인이 충돌하면 조건 확인 전 최종 확정하지 않는다.
- `presentation.status`는 `pending | dirty | ready`다. 최초에는 `pending`, 시간·출처·Q&A 조건 변경 시에는 `dirty`로 두며 deck·pitch·cue·fallback 재검수와 실제 리허설 전에는 `ready`가 아니다. 공식·Q&A 미확인 상태에서는 최종 `ready`로 승격하지 않는다.

`/init`에서 기록하고 `/adapt`에서 행사 전에도 갱신한다. 변경 기록에는 이전 시간/출처, 새 시간/출처, Q&A 조건, 영향받는 deck·pitch·demo cue·fallback, 승인된 재작업 범위와 남은 검수를 남긴다. 60초 provisional → 공식 120초는 `effective_seconds = 120`, `timing_status = official`, `status = dirty`이며 발표 재검수 대기다. 시간이 늘어도 임의의 기능·시장·팀 소개로 채우지 않는다. 줄면 핵심 전후 결과는 보존하고 덜 중요한 정보를 삭제한다. 독립 expected와 실제 evidence는 변경하지 않는다.

[workflow 계약](workflow-policy.md)과 [adapt](../.claude/commands/adapt.md)의 환경설정 전용 예외를 적용한다. preparation.md가 없어도 발표 조건 기록 또는 구현 전 최초 계정 설정 점검은 승인 범위 안에서 가능하다. adaptation.md에 목적·허용 출처·실제 점검·제품 미구현·E2E 미실시·재개 조건을 기록한다. 제품 연결 모드는 preparation.md와 보존·복구 확인이 필요하다. 시간 기록 완료, 환경설정 점검 완료, 제품 연결 완료, presentation 완료는 서로 다르다.

## 신규 deck의 추천 제작 흐름과 완료 기준

1. 공식 조건·유효시간·Q&A·독립 evidence와 build_policy의 deck/pitch/submission 개별 사전 허용을 확인한다. 금지·unknown이면 작성 보류이며 초안도 예외가 아니다. 최신 신규 출품물의 자격이 확인된 실제 evidence만 결과로 사용한다. 긴 투자 문서나 전체 프레임을 60초에 밀어 넣지 않는다.
2. 짧은 발화 초안부터 쓰고 핵심 변화 한 가지를 정한다. 여기의 초안은 `/deck`의 서사 설계이며 `/pitch` 필수 입력을 우회한 완료가 아니다.
3. 메시지·근거·화면·초수로 slide map을 만든다. 시간 안에 필요한 메시지·실제 핵심 데모·가독성으로 장수를 결정하며 장수 기본값은 없다.
4. 메시지·실제 핵심 데모·가독성 검토에 필요한 장면을 representative renders로 선정해 사용자 검토·승인을 받는다. 대표 렌더 개수 규정은 없다. 데모가 외부 live 화면이면 해당 실제 화면과 전환을 함께 검토한다. 승인 전 전체 제작으로 넘어가지 않는다.
5. 승인된 방향으로 전체를 제작하고 실제 전체 렌더를 확인한다. 렌더하지 못하면 시각 검수 대기이며 완료가 아니다.
6. 기술 QA는 실행 evidence, 독립 expected, 링크·파일·overflow 등을 확인한다. 설득/시각 QA는 처음 보는 사람이 문제·핵심 변화·차별을 이해하는지, 핵심 화면이 읽히는지, 시선과 발화가 맞는지 별도로 확인한다. 테스트 수나 screenshot 잘림 없음은 발표 품질 완료의 증거가 아니다.
7. `/pitch`에서 발화·demo·cue·fallback을 맞추고 실제 화면과 발화로 두 번 연속 시간을 잰다. 수행자·일시·자료 버전·측정 초수를 기록한다. 계산상 예산이나 자동 타이머 테스트는 실제 리허설이 아니다. 미실시이면 그대로 표시한다.
8. `/preflight final`에서 공식 조건, YAML, deck, 대본, demo cue의 시간 일치와 총합을 대조한다. 변경 뒤의 자료가 아니거나 승인·렌더·리허설이 남으면 발표 준비 완료로 표시하지 않는다.

## 현재 사용자와 합의한 조건

현재 Base44/Daytona 발표 준비의 Q&A 없음 전제는 사용자 확인(`user-confirmed`)에 근거한다. 공식 확인(`official`)은 아니다. 해당 준비에서는 `qa_mode: none`, `qa_seconds: 0`을 적용하며 공식값과 사용자 확인 시간 모두 없을 때만 준비 기본60초를 적용한다. 다른 행사에는 이 전제를 전파하지 않는다. 공식 안내와 충돌하면 공통 변경 계약에 따라 재확인한다.

이번 정정은 공통 규칙만 다룬다. 행사 workspace 갱신과 Base44/Daytona 실제 deck 재제작 요청 전달은 부모 스레드가 담당하며 이 정정으로 재제작을 실행하지 않는다.

현재 이 가이드 작성은 실제 deck 제작·렌더·발표 리허설의 실행 결과가 아니다.
