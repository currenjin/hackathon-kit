# 현장 상태와 행사 종료 점검

기존 `/adapt`, `/preflight`, `/submit`, `/archive`의 보완 계약이다. 새 slash command나 필수 YAML schema를 추가하지 않는다. 기존 notes·closeout·인계 문서가 같은 역할이면 재사용하고, 과거 행사를 일괄 변환하지 않는다.

## 제출과 조건부 발표

제출 후 대표·결선 발표자를 선정하는 행사는 두 검수 범위를 분리한다.

1. `/submit` draft와 `/preflight final`의 **제출 범위**는 실제 폼의 필수 산출물, 제품 evidence, 공개 접근과 마감을 검사한다. 폼에 필요한 영상·발표 자료는 이 범위에서도 검사한다.
2. 최종 발표가 선정 후에만 필요하면 `선정 대기`를 명시한다. 선정되지 않았다는 이유로 제출 검수를 미완료로 만들거나, 제출 완료를 발표 ready로 바꾸지 않는다.
3. 선정되면 `/adapt`로 시간·형식·근거와 영향받는 자료를 갱신하고 `/deck`, `/pitch`, `/preflight final`의 **발표 범위**를 재개한다. 조건 변화 뒤에는 기존 자료를 dirty로 두며 자동 재제작하지 않는다.

이 분기는 제품 검증·공식 자격·제출 전 final 검수를 생략하는 예외가 아니다. 실제 제출은 사용자가 하며 이미 제출한 문구와 당시 버전은 보존한다.

## 확인 출처와 제출 상태

- `draft`: 실제 제출 완료 보고나 접수 근거 없음.
- `submitted_user_confirmed`: 사용자가 완료를 보고했지만 접수 화면·메일·레코드를 직접 확인하지 못함. 보고 원문·시각 또는 시각 미확인·당시 자료 버전을 기록한다.
- `submitted`: 접수 화면·확인 메일·등록 레코드로 확인. readback 근거를 연결한다. 기존 submitted 기록을 새 필드 부재만으로 소급 강등하지 않는다.

사용자 보고를 직접 접수 검증으로 승격하지 않고, 로그인 벽 때문에 이미 확인한 사용자 보고를 draft로 되돌리지 않는다. 수정 초안은 제출 상태와 별도다. 실패·미접근·미실행도 구분한다.

발표 시간은 [발표 시간 계약](presentation-reference-guide.md#시간의-단일-기준과-변경-계약)을 따른다. 공식값, 사용자 확인 범위, 준비 목표와 기본값을 구분한다.

## 공개할 범위와 보관 경계

공개가 승인됐을 때만 현재 트리·도달 가능한 이력·다른 제품 자료·이미지·데이터·라이선스 상태의 검사 범위를 적는다. secret 검사 성공과 최종작만 공개한다는 범위 검사는 다른 항목이다. PUBLIC과 오픈소스 라이선스 부여도 구분한다.

다른 제품 이력이 있다는 이유만으로 새 저장소·새 루트·force push를 실행하지 않는다. 기존 저장소 유지, 공개 대상 분리, 이력 정리의 선택지와 영향을 알리고 해당 작업의 별도 승인을 받는다. 이력 정리는 백업·무결성·복구 확인과 SHA 대응표를 남기며 과거 증거를 재작성하지 않는다. main에서 제거한 커밋이 서버·캐시에서 즉시 삭제됐다고 주장하지 않는다.

## 기록 완료와 운영 종료

`/retro`·링크 정리 완료와 운영 종료 확인을 별도로 보고한다. 운영 점검은 먼저 목록과 선택을 기록하며, 자격증명 조회·삭제·외부 쓰기 권한을 새로 부여하지 않는다.

- 본 앱·시험 앱별 유지 / 종료 / 사용자 결정 대기와 소유 경계.
- 배포·함수·secret·엔티티 시험 데이터·저장 객체·비용 발생 가능 자원.
- 승인한 조치, 실제 결과, 확인 시각과 readback. 비지원·미실행·확인 불가를 삭제 완료로 취급하지 않음.
- 역사적 제출·검증 URL과 현재 서비스 상태. HTTP200인 종료 안내 페이지는 제품 운영 성공이 아님.
- README·About·references의 링크 상태와 현재 요약을 함께 대조. 과거 제출·검증 사실은 그대로 보존.

현재 요약은 기존 closeout·notes·인계 문서 중 한 곳에 두고 기준 시각과 근거를 붙인다. 구조화가 필요할 때만 예를 들어 `closeout.service_status: ended`를 쓴다. 당시 deployed 설명은 역사라고 표시하며 현재 운영 설명과 섞지 않는다.

증거는 민감도를 고려해 위치·해시·접근 경계·복구 확인 여부를 기록한다. 앱과 옛 공개 SHA 없이 필요한 파일·관측을 다시 읽을 수 있는지 확인한다. 개인정보가 있는 원본을 무조건 저장하지 않고 최소 비민감 증거와 미보관 한계를 남긴다. 번들 파일 존재와 복구 검증 완료는 다르다.

## 읽기 전용 보조 검사

```sh
python3 -B tools/workflow_checks.py workspace/<event-slug> --scope submission
python3 -B tools/workflow_checks.py workspace/<event-slug> --scope presentation
python3 -B tools/workflow_checks.py workspace/<event-slug> --scope archive
```

검사기는 YAML과 연결된 JSON contract를 읽고 진단 코드만 출력한다. 파일 수정·앱 접속·계정 조작·마이그레이션은 하지 않는다. 진단이 있으면 종료코드1이며 제품 FAIL이나 제출 금지를 자동 결정하지 않는다. 과거 기록에 선택 필드가 없으면 원문부터 확인하고 새 값을 추정해 넣지 않는다.

`RECEIPT_NOT_READ_BACK`은 제출 실패가 아니라 사용자 보고와 직접 검증의 차이다. `PRESENTATION_SOURCE_UNVERIFIED`는 기록된 시간을 보존하되 출처·상태를 수동 확인해야 한다는 뜻이며, 출처 없는 비기본 시간을60초로 덮지 않는다.

구조가 잘못된 YAML·contract는 진단 JSON과 종료코드1로 반환하고 원문·예외 내용을 출력하지 않는다. `HISTORICAL_READINESS_UNVERIFIED`는 발표 완료 보고를 부정하는 것이 아니라 당시 ready 검수의 별도 근거가 없다는 뜻이다. `CURRENT_SERVICE_STATE_UNRECORDED`는 notes를 포함한 수동 대조가 필요하다는 뜻이다.

필드 일치·정적 테스트 통과는 실제 브라우저 검증·공식 근거 확인·리허설의 대체가 아니다.
