# 행사 자료와 실행 기록 인계

[workflow 계약](workflow-policy.md)과 [사전 준비 완료 기준](pre-event-readiness.md)을 구체적인 양식으로 읽는 방법이다. 새 command나 YAML schema, 별도 제품 검증체계를 추가하지 않는다. 이 공통 문서 변경은 행사 선택·제품 구현·외부 공개·제출 승인이 아니다.

## 저장과 승인

- 모든 행사 기록은 확정된 `workspace/<event-slug>/` 안에 둔다. 제품 코드는 원래 제품 저장소 또는 확인된 hosted app에서 관리한다.
- 기존 경로와 문서 절을 먼저 찾는다. 기존 `submission-fact-sheet.md`, `preparation.md`, slide map, 증거표가 같은 역할을 하면 그대로 사용하고 연결한다. 동일 사실의 두 번째 원본을 만들지 않는다.
- 적합한 기록이 없을 때만 해당 양식의 필요한 절을 사용한다. 파일명·파일 수를 완료 조건으로 만들지 않으며, 기존 workspace를 자동 migration하지 않는다. `hackathon.yaml` notes나 기존 인계 문서에 채택 경로를 적어 다음 command가 찾게 한다.
- 행위별 공식 허용과 사용자 승인을 먼저 확인한다. 금지·unknown인 기획·설계·criteria·코드·자료를 양식 채우기로 우회하지 않는다. 가능한 기록만 남기고 보류 사유를 표시한다.
- 다음 command, 계정 생성, 도구 설치, 유료 호출, 배포, 공개와 제출은 자동 실행하지 않는다. 별도 승인 경계를 유지하며 실제 제출은 사용자가 한다.
- 과거 행사와 이미 제출한 문구·접수 사실을 소급 변경하지 않는다. 이 양식으로 과거 실행·승인·성과를 만들어 넣지 않는다.

## 1. 공통 사실표

[공통 사실 양식](../templates/project-facts.md)은 발표 자료가 공유할 사실의 색인이다. 원문과 실행 evidence를 대체하는 증거 원본이 아니다.

- `/ideate`는 허용된 명세 안에서 사용자·문제·입력→행동→결과·지원/제외 범위를 기록한다. 미결정을 확정하지 않는다. 별도 사실표를 즉시 만들 필요는 없다.
- `/deck`은 자료 작성을 시작할 때 기존 사실표를 찾고, 없으면 관련 기록을 연결한 사실표를 만든다. `/pitch`와 `/submit`은 같은 기록을 읽고 승인된 범위의 새 사실과 출처만 보완한다. 공통 사실이 비어 있으면 저장소와 기존 기록부터 확인하고 정말 필요한 질문만 한다.
- 각 claim에는 출처, 현재 build 또는 자료 버전, 검증 경로(local/mock/실제 provider), 사용 가능 범위와 한계를 붙인다. 제품명·채택 sponsor·공개 URL은 각 소유 기록과 대조한다. 새 수치나 수상 결과를 채우지 않는다.
- 충돌은 최신처럼 보이는 문장으로 덮지 말고 원문·독립 contract·실제 실행과 대조한다. 충돌이 해결되지 않은 claim은 성과에서 제외하고 미확인으로 남긴다. ORACLE INVALID / UNVERIFIED와 local/mock 한계는 모든 언어에서 유지한다.
- 제품·설정·독립 판정·시간 조건·명칭·링크가 바뀌면 변경 영향과 영향받는 deck/pitch/guide/submission 버전을 기록한다. 기존 사실표와 배포된 문구를 조용히 덮어쓰지 않는다. `/adapt`는 사실·영향·재검수 대기를 기록하고 다른 command를 실행하지 않는다.
- `/preflight final`은 실제 산출물의 claim과 사실표의 근거를 대조하고 검수한 버전을 기록한다. 같은 문구가 반복된다고 사실 검증이 된 것은 아니다. 불일치가 있으면 해당 자료의 일관성 검수 대기이며 기존 presentation pending/dirty 계약을 유지한다. 정적 검사 성공만으로 ready가 되지 않는다.

## 2. 현장 실행표와 최초 호출

[현장 실행 양식](../templates/execution-plan.md)을 `preparation.md` 또는 기존 runbook에 필요한 만큼 사용한다.

- `/prepare`의 허용된 작업계획은 작업마다 담당, 확인 시점, 눈으로 확인할 완료 증거, 미달 시 축소/중단/대체 경로를 연결한다. 공식 제작 시작·종료·제출 마감과 지참 기기에 맞춘다. 정해진 6/12/24시간 계획을 강제하지 않는다.
- 가장 위험한 가설의 최소 확인 → 첫 E2E → 조기 배포/실행환경 확인 → 검증 → 발표·영상·제출 준비와 백업을 다룬다. 모든 제품에 DB·인증·두 번째 기능을 추가하지 않는다. 배포가 불필요하면 실제 실행·전달 경로를 확인한다.
- 팀 행사일 때만 구현·통합·발표·제출의 담당과 합치는 시점을 정한다. 혼자라면 역할표를 따로 만들지 않는다. 사용자가 맡지 않은 역할을 임의로 배정하지 않는다.
- `/init`의 sponsor 공식 조사에서 출처를 이어 받고, `/prepare`는 채택된 sponsor의 최초 호출 안내를 기록한다. `/adapt`는 승인된 실제 설정·호출 결과를 갱신한다. 호출 명령이나 prompt의 사전 작성도 해당 행위 허용 안에서만 한다.
- 최초 호출 안내는 인증 경로·환경 변수 이름·최소 입력/실행 경로·독립 기준·정상 결과의 확인 방법·권한/금액/외부 전송·timeout/재시도 한도·오류 대응을 포함한다. secret 값·개인정보를 적지 않는다. 실제 쓰기는 승인과 readback을 분리한다.
- 안내 작성, SDK import, mock 성공, 실서비스 호출 성공, 실제 제품 E2E를 각각 구분한다. 자격·quota·계정 미지급으로 불가능한 실행은 이유와 최초 확인·축소 조건을 남긴다. 체크 표시로 미실행을 성공으로 바꾸지 않는다.

## 3. 공식 기준과 증거 연결

[심사 기준별 증거 양식](../templates/judging-evidence.md)을 기존 slide map 또는 제출 준비 기록에 연결한다.

- `/deck`은 공식 기준 원문과 출처, 보여줄 장면, 실제 실행 evidence, 해당 build와 경로를 연결한다. `/pitch`는 같은 기준에 발화·화면 cue를 연결하고 `/submit`은 실제 폼에 필요한 주장만 사용한다.
- 기준이 미확인이면 그대로 남긴다. 일반 가이드의 가중치나 예상 심사 점수를 공식 기준으로 만들지 않는다. 공식 목표나 참가 요건은 심사 기준과 별도 제목으로 기록한다.
- 기준 충족을 보여줄 근거와 제품 PASS는 다르다. 이 표는 점수 보장·출품 자격 판정·독립 demo contract를 대신하지 않는다. 상속한 starter와 행사 중 새로 만든 부분도 구분한다.
- `/preflight final`은 발표·제출의 실제 장면과 근거를 대조한다. 자료에서 인용한 미검증 주장은 제외 또는 한계로 수정하고, 실행 미실시·부적격·접근 불가를 숨기지 않는다. 심사 기준 미확인만으로 기존 제품 실행 결과를 FAIL로 바꾸지는 않는다.

## 4. 예시와 기술 레퍼런스

- [합성 작성 예시](../examples/synthetic-handoff.md)는 양식을 읽는 방법이다. 실제 행사 evidence나 사용자 승인으로 재사용하지 않는다.
- [조건부 스타터 목록](starter-references.md)은 제품 유형에 맞는 참고 자료다. `/ideate`와 `/prepare`에서 필요할 때만 검토하며 기본 스택이나 추가 설치를 강제하지 않는다.
- `AGENTS.md`의 독립 expected, oracle 격리, 소유·복구·게시 계약과 [workflow 계약](workflow-policy.md)의 기존 충돌 처리 규칙은 그대로 유지한다. 이 문서 추가로 권한 충돌이 사라졌다고 주장하지 않는다.
