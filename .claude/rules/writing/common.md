# Writing — Common

사람이 읽는 deck, pitch, submission, README, issue, report에 공통으로 적용한다. [workflow 계약](../../../references/workflow-policy.md)의 행위별 제작 허용을 먼저 확인한다. 문체 수정·번역으로 사전 작성 금지를 우회하거나 historical/미확인/재검수 상태를 지우지 않는다.

## 사실

- 사실, 수치, 날짜, 고유명사, 코드, 파일 경로, 링크를 글투를 다듬는 과정에서 바꾸지 않는다.
- 검증하지 못한 내용을 완료된 기능이나 확인된 결과처럼 쓰지 않는다.
- demo, deck, pitch, submission은 같은 source of truth를 쓴다.
- deck과 pitch의 숫자는 현재 행사 workspace의 demo contract와 실제 실행 결과에 맞춘다.

## 문장

- 한 문단은 3문장을 넘기지 않는다.
- 한 문장에 한 메시지를 둔다.
- 단정할 수 있으면 단정한다. 근거 없는 확신이나 습관적인 헤지를 붙이지 않는다.
- 추상적인 범주어보다 실제 제품명, 컴포넌트명, 기술명을 쓴다.
- 기술 용어는 업계에서 통용되는 표준 용어를 쓴다.
- 같은 사실이나 근거를 여러 곳에 복사하지 않는다.

## 구조

- 표, 불릿, 체크리스트, 헤딩, 다이어그램은 스캔을 위한 구조라서 산문으로 합치지 않는다.
- 그림이나 표가 이미 보여준 내용을 바로 아래 산문으로 반복하지 않는다.
- 결론에 필요한 근거와 트레이드오프는 남긴다. 짧게 쓴다는 이유로 삭제하지 않는다.

## 장식

- em-dash(—)로 문장을 잇지 않는다.
- 볼드는 한 문단에 한두 개만 쓴다.
- 이모지를 문서 구조에 쓰지 않는다.
- 의미 없는 수식어와 과장 표현을 줄인다.

## 발표용 글

- 먼저 문제를 이해시키고 구현 세부는 demo 흐름에서 설명한다.
- 심사 기준을 직접 주장하기보다 실제 화면, 수치, 실행 결과로 보여준다.
- sponsor는 이름을 나열하지 말고 제품 흐름에서 맡는 역할을 설명한다.
- slide 한 장에는 메시지 하나를 둔다.
- pitch 문장은 소리 내어 읽었을 때 자연스러워야 한다.

## 여러 언어

- 한 언어로 쓴 문장을 다른 언어로 직역하지 않는다.
- 같은 사실을 유지하되 각 언어의 자연스러운 문장 구조로 다시 쓴다.
- 제품명, API, SDK, 코드 식별자, 표준 기술 용어는 임의로 번역하지 않는다.
