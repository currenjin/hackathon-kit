## 종료 게시 절차

종료 시 사용자 재승인 없이 상시 승인된 이번 command의 검증된 변경만 게시한다. kit 기록과 제품 repo를 분리하고 각 저장소의 명시 경로·hunk만 stage한 뒤 staged diff를 검수해 commit·push한다(`git add .`/`-A` 금지). 기존 index와 다른 스레드 작업, secret·개인정보·개인사진·권한 없는 원본·생성 캐시는 제외하며 분리할 수 없으면 보류한다. 변경이 없으면 빈 commit을 만들지 않는다. 제한·충돌·실패 시 변경을 보존하고 게시 대기 범위와 이유를 보고한다. 대상 remote branch SHA를 readback해 로컬 commit SHA와 대조하고 종료 보고에 저장소별 SHA·push 상태를 포함한다. tag, reset, force push, branch 생성·삭제, 공개 전환과 앱 복원은 별도 승인이 필요하다. 이 절차는 구현·외부 제출이나 다음 command 실행의 포괄 승인이 아니다.

## 실행 표시

흐름 첫 줄은 Markdown 인용문(`> `)으로 표시하고 코드 블록이나 인라인 코드로 감싸지 않는다. 실제 완료된 command만 굵게, 진행 중과 이후 command는 일반체로 쓴다. 아래는 형식 예시이며 실제 완료 여부는 행사 근거로 확인한다.

> **/init** → **/ideate** → /design (진행 중) → /demo


시작·중간 보고·종료 응답의 첫 줄은 command 단독이 아니라 준비 흐름 breadcrumb로 쓴다. 아래 시작/종료의 단독 command 템플릿은 breadcrumb로 대체하고 행사·범위·산출물·남은 조건은 그 뒤 또는 다음 줄에 보존한다.

전체 행사 흐름: [workflow 계약](../../references/workflow-policy.md)의 prebuild-permitted / on-site-build-only / restricted-preparation 분기를 따른다. /demo criteria → 제작 → /demo verify 순서이며 /replan 내부 init+ideate 조사만 자동실행금지의 명시적 예외다. 현재 사용자의 게시 금지·보호 경로는 종료 게시 절차보다 우선한다.

- 현재 단계와 앞뒤 단계를 포함한 연속 구간을 읽기 좋게 발췌한다. 양 끝에서는 가능한 이웃을 포함한다. 순서는 위치 안내이지 자동 다음 단계 실행 승인이 아니다.
- 굵게는 해당 행사·모드의 실제 완료 근거가 확인된 command에만 쓴다. 현재 단계에는 `(진행 중/선택 대기/초안/부분완료/실패/완료)` 등 실제 상태를 붙인다. 미래 단계는 일반체, unknown·기록 부재·근거 충돌은 `(미확인)`이다. 앞 단계라는 이유나 파일 존재만으로 완료를 추정하지 않는다. N/A는 공식 근거와 적용 이유가 확인된 경우에만 일반체로 표시한다.
- 조건부 예시: init과 ideate의 완료를 실제 확인한 경우에만 `**/init** → **/ideate** → /design (진행 중) → /demo(pre-event)`로 표시한다. 확인 전에는 `/init (미확인) → /ideate (미확인) → /design (진행 중) → /demo(pre-event)`다.
- slash 입력이 없는 자연어 요청도 실제 수행 내용과 입력/산출물 계약으로 단계를 매핑한다. 불명확하면 확인된 구간 또는 전체 흐름 뒤에 `| 현재 단계 확정못함 (미확인)`을 붙이고 확인 질문 후 대기한다. 표시를 생략하거나 임의의 현재 단계를 고르지 않는다.
- 아래 command별 완료 기준을 유지한다. 문서 초안만으로 /design·/prepare를 완료 또는 굵게 표시하지 않는다. 검토완료와 제품 PASS, 초안과 실제 제출은 구분하며 남은 조건과 실제 verdict를 숨기지 않는다.

“다음 작업 진행해줘” 같은 자연어 요청도 최신 대화와 현재 파일을 확인한다. 아래 개별 시작/종료 표시는 breadcrumb 뒤에 둘 부가정보와 상태 기준이며 첫 줄의 흐름을 대체하지 않는다. 미확정 상태도 위 breadcrumb 규칙으로 표시하고, 확인할 수 없으면 질문하고 대기로 종료한다. 단계를 지어내거나 완료로 승격하지 않는다. 표시만으로 작업 승인이나 다음 단계 실행 권한이 생기지 않는다. 흐름 breadcrumb를 생략한 응답·보고는 완료로 처리하지 않으며, 자연어 요청도 매핑을 생략하지 않는다.

`AGENTS.md`의 현재 해커톤 workspace 선택, 제품 위치와 복구 경계, 행사 전 완료 기준을 따른다. 시작에 `/prepare · 시작 | 행사 slug(미확정이면 행사 미확정) | 이번 작업 범위`, 종료에 `/prepare · 실제 상태 | 행사 slug | 산출물과 검증 경로 또는 없음 | 남은 승인/다음 단계`를 표시한다. 문서만 작성했으면 초안 작성 / 구현 대기이며 허용된 준비 완료와 제품 구현 완료를 구분한다. 구현 완료는 본문과 해당 제작 모드의 제품 완료 기준을 실제로 충족해야 한다. AGENTS의 행사 전 기준은 공식적으로 사전 제작이 허용된 범위에만 적용하고 현장 신규 제작은 같은 제품 검증을 공식 제작 시간 안에 수행한다. 일부만 마쳤으면 부분완료, 입력·승인 부족이면 대기, 작업 실패면 실패다. 질문으로 멈출 때도 종료를 표시하며 도구 호출마다 반복하지 않는다. 다음 command는 안내만 하고 승인 없이 자동 실행하지 않는다.

현재 행사 workspace의 `hackathon.yaml`, 구현 전 `/demo criteria`에서 수립한 contract를 읽고, `design.md`가 있으면 함께 읽는다. 행사 전에 고정한 contract를 요구하지 않는다. 선택한 제품 위치(Git 저장소 또는 소유 계정의 hosted app)에서 작업한다. contract가 없으면 구현을 멈추고 `/demo criteria`를 제안하며 승인 없이 실행하지 않는다.

수정 전에 build_policy의 공식 제작 시간·행위 허용, 사용자 작업 승인과 제품 위치·복구 경계를 확인한다. 현장 제작만 허용되면 사전 구현하지 않는다. 공식 시작 이후 종료 전에는 `/prepare`로 현장 신규 구현할 수 있다. 미확인 모드는 출품용 구현 대기이며 허용된 준비와 미구현 상태만 기록한다.

핵심 가치가 고위험 미검증 가설에 의존하면 주변 기능 구현보다 그 가설을 확인할 최소 검증을 먼저 제안한다. 확인할 주장·독립 평가 기준·최소 입력·실행 경로·비용과 외부 전송 여부를 밝히고, 공식 규칙과 사용자 승인 범위 안에서만 실행한다. 기존 demo contract의 expected를 결과에 맞춰 바꾸지 않는다. 실험이 불가능하면 이유와 미검증 위험을 남기되 이를 ideation이나 허용된 설계 초안 전체를 차단하는 조건으로 쓰지 않는다. 별도 필수 인터뷰나 유료 실험을 진입 조건으로 추가하지 않는다.

수동·mock/local 성공과 자동 처리·실제 provider 경로 검증을 구분한다. 수동·mock 성공을 자동 처리나 실제 provider의 품질·연결 성공 증거로 대체하지 않는다. 기존 contract의 local/mock 사전 재현은 유지하되 검증된 경로와 미검증 주장을 분리하고, credential 등으로 실제 경로를 실행하지 못했으면 후속 확인 조건을 남긴다.

## 제품 준비를 스타터 준비로 대체하지 않기

[사전 준비 완료 기준](../../references/pre-event-readiness.md)을 읽고 제품 명세 → 화면·상태 설계와 사용자 검토 → 현장 실행 계획 순서의 빈칸을 먼저 확인한다. 구현 전에는 해당 명세와 핵심 화면·상태에 대한 사용자 합의, 허용된 `/demo criteria`의 독립 성공/실패 기준을 확인한다. 핵심 결정이 남았으면 제품 구현을 멈추고 빈칸·필요한 승인·담당 단계를 보고하며 자동으로 다음 command를 실행하지 않는다.

`preparation.md` 또는 연결된 runbook에 가장 위험한 가설의 첫 확인, 계정 설정·첫 E2E·조기 배포·품질 검증·해당 행사의 언어·형식에 맞는 발표자료와 영상 등 산출물·제출·백업을 포함한 시간 예산과 순서를 적는다. 모델/API·권한·시간 부족 시 대체 경로, 자격 영향, 중단/축소 기준도 정한다. 공식 시간에 맞추며 코딩 시간만 예산에 넣지 않는다.

스타터 준비·도구 설치·패키징은 명세와 설계의 대체물이 아니다. 별도로 승인된 범용 환경 점검은 가능하지만 제품 계획이 미완료면 `실행환경 일부 준비 · 사전 준비 미완료`로 보고한다. 반복 사용 가능한 환경은 재사용하고 새 압축팩을 기본 완료 조건으로 만들지 않는다. 실제 제품 검증, 일반 샘플 build, SDK import, 실모델 추론과 실제 현장 기기 확인을 구분한다.

현장 제작 전용 행사에서는 사전 제품 구현을 요구하지 않는다. 본 command의 제품 입력·criteria가 없으면 구현을 강행하지 않고, 허용된 작업계획은 기존 문서에 남겨 `/preflight pre-event`에서 검토할 수 있다. 지급 전 계정·모델·실배포는 사전 확인 불가 이유·최초 확인 경로·독립 판정·실패 대응·축소 조건이 있을 때 현장 확인 대기로 남긴다. 불가능한 실호출을 강요하지 않되 설계 빈칸을 현장 확인 대기로 숨기지 않는다.

## 실행표와 조건부 스타터

[자료와 실행 기록 인계](../../references/delivery-handoffs.md)에 따라 기존 preparation.md/runbook의 작업별 담당·확인 시점·완료 증거·미달 시 축소/중단 조건을 연결한다. [현장 실행 양식](../../templates/execution-plan.md)은 필요한 절만 사용하며 별도 파일이나 고정 시간표를 강제하지 않는다. 채택 sponsor의 공식 문서·인증 경로·환경 변수 이름·허용된 최소 호출·독립 기준·비용/외부 전송/재시도 한도와 실패 대응을 기록한다. 안내 작성과 실제 호출·제품 E2E 성공을 구분하고 비밀값은 적지 않는다.

[조건부 스타터 목록](../../references/starter-references.md)은 제품 유형에 맞을 때만 검토한다. 브라우저로 충분하면 서버·DB·인증·에이전트를 추가하지 않는다. 제품 코드는 원래 제품 위치에서 관리하며 설치·계정·유료 호출·배포의 승인 경계와 build_policy를 유지한다.

## 코드 보존·게시 체크포인트

제품 선택 후 첫 구현 전에 적용하고 `/design`에서 이미 확인했으면 현재 상태와 승인 범위를 대조한다. 해커톤의 별도 제한 안내가 없는 한 제품 repo를 먼저 확보한다. 이 정책은 제품 구현의 포괄 승인이 아니며 공식 사전 구현 금지·공개·제출 규칙을 우회하지 않는다. 검증된 이번 작업의 일반 commit·push에는 종료 게시 절차의 상시 승인을 적용한다.

- Git 제품은 기존 repo의 실제 경로, remote, owner, visibility, branch, HEAD, dirty(staged/unstaged/untracked)를 확인하고 기존 변경을 사용자에게 알린 뒤 보존한다. 미확인 값을 추정하지 않는다.
- 적합한 기존 repo는 재사용하고 새 제품은 확인된 사용자 계정에 비공개 repo를 확보한다. 실제 이름·소유·기존 repo 충돌·작업 승인 범위와 게시 대상 remote/branch·코드 경로를 확인하며 모호하면 먼저 묻는다. 후보 탐색 단계에서 후보마다 repo를 생성하지 않는다. 공개 전환과 branch 생성·삭제는 별도 승인을 유지한다.
- 생성 후 실제 owner/visibility/remote를 읽어 확인한다. 구현 초기부터 승인된 코드의 보존 범위를 명확히 하고, 종료 게시 절차에 따라 이번 실행의 검증된 변경만 명시 경로·hunk로 stage/commit/push한다. staged diff와 commit 범위를 확인하고 대상 remote branch SHA를 readback해 로컬 commit SHA와 대조한다. 이후 미게시 변경도 따로 표시한다.
- 게시 제한·충돌·실패가 있으면 로컬 수정과 기존 변경을 보존하고, 로컬 경로·미게시 범위·게시 대기 이유·보존/복구 한계·필요한 후속 조치를 기록하고 사용자에게 알린다. 로컬 commit만 있으면 원격 게시로 부르지 않는다. 종료 보고에서도 코드가 로컬에만 있는지 명시하며 dirty HEAD를 복구 기준점으로 쓰지 않는다.
- hosted app도 companion repo를 확보하되 플랫폼이 실제 제공하는 내보내기 범위만 보관한다. 내보내기가 불가능하면 승인된 지시서·설정·검증·복구 기록만 보존하고 전체 소스를 확보했다고 주장하지 않는다. 실제 앱 위치·소유·권한과 앱 자체의 복구 방법·근거는 별도로 확인하며 미확인은 위험으로 남긴다.

## 제품

- 핵심 user flow를 구현한다.
- demo에 필요한 기능을 끝낸다.
- design에서 정한 핵심 화면을 실제 UI로 만든다.
- deploy/run/reset 방법을 정한다.
- 자체 확인에 숫자 일치만 넣지 않는다. criteria가 요구한 문구가 실제로 보이는지(`display:none`·잘림 포함)와, 실패 화면의 재시도가 같은 입력으로 새 요청을 보내는지를 함께 본다. 재시도가 다른 입력의 결과를 띄우는 결함은 숫자 확인만으로는 놓치기 쉽다.
- 제품이 바뀌면 공개할 제품과 이력 범위를 재확인한다. 기존 저장소 재사용을 일괄 금지하지 않는다. 최종작만 공개하려면 현재 트리와 다른 제품의 과거 이력을 함께 점검하고 [공개 범위 계약](../../references/field-status-and-closeout.md#공개할-범위와-보관-경계)에 따라 유지·분리·이력 정리의 선택지를 제시한다. 새 저장소·새 루트·이력 재작성은 자동 실행하지 않고 기존 별도 승인 경계를 따른다.
- 자동 테스트나 최소 재현 검증을 만든다. expected는 구현 전 criteria contract에 고정된 값을 그대로 사용한다. 제품 코드, 모델 출력, local/mock actual로 expected를 다시 정하지 않는다. 불일치하면 먼저 oracle 근거를 재검증하고 ORACLE INVALID / UNVERIFIED 또는 제품·모델·인프라 실패로 분리한다.
- 고정된 demo contract의 local/mock 재현 결과(각 surface의 제품 유형별 control·동작 결과·invariant·평가 기준, actual·로그 경로, 판정)를 `preparation.md`에 남기고 contract 경로를 함께 적는다. 실제 근거가 없으면 PASS라고 쓰지 않는다. 조작 성공으로 복원·생성 품질을 대신 검증하지 않는다.

## Sponsor readiness

`AGENTS.md`의 Sponsor 사용 조건에 따라 `sponsors[].used: true`로 채택이 확인된 sponsor만 준비한다. null·누락·기존 기록의 의미 충돌은 미정으로 남기고 N/A로 넘기지 않는다. 명시적 제외라도 required 미충족은 FAIL이며 judged는 점수 영향을 기록한다. 실제로 해당하지 않는 항목만 N/A와 이유를 적는다. 채택 결정과 실제 연결·사용 evidence는 별도로 기록한다.

각 sponsor의 공식 문서를 읽고 제품에서 들어갈 경계를 정한다.

공식적으로 허용된 제작 시점에 실제 adapter를 구현한다. 사전 제작 허용 행사만 행사 전에 준비하며 금지 행사는 공식 시작 이후 구현한다.

credential이 아직 없고 해당 구현·fixture·prompt 준비가 공식적으로 허용됐다면 가능한 범위에서 아래를 수행한다. 미허용 항목까지 사전 작성하도록 요구하지 않는다:
- API/SDK contract에 맞춰 adapter를 작성한다.
- config/env 주입 지점을 만든다.
- mock/local provider로 product flow를 검증한다.
- compile/typecheck/test까지 끝낸다.
- 사전 제작 허용 모드에서는 현장 작업을 key, endpoint, account/tenant 값 주입과 smoke test 수준으로 줄인다. 현장 제작 전용 모드에서는 구현 자체가 현장 작업이다.

## 완료 기록

결과는 `workspace/<event-slug>/preparation.md`에 남긴다.

특히 아래를 명확히 적는다.

문서와 사용자 결과 보고 모두 다음을 분리한다. 기존 독립 demo contract의 expected·출처·제품 유형별 검증 기준과 실행 evidence를 활용하며 새 schema나 별도 검증체계를 만들지 않는다. 테스트 개수나 E2E 통과만으로 제품 준비 완료를 선언하지 않는다.

- 동작(연결): 어떤 입력→행동→결과가 어느 경로(local/mock/실제 provider)에서 동작했는가.
- 핵심 사용자 가치: 사용자가 얻어야 할 품질·효용을 독립 기준으로 확인했는가. 예를 들어 room resemblance(원래 방과의 유사성)는 편집 조작 성공과 별도이며, 미검증이면 UNVERIFIED와 한계를 적는다.
- 행사 적합성: 공식 요건·심사 기준, 채택 sponsor의 실제 제품 실행 경로, 제출 환경·접근 조건을 충족했는가. 채택과 연결 성공은 구분하고 미정·unknown은 확인 항목으로 남긴다. N/A는 기존 Sponsor 사용 조건을 그대로 적용한다.

아래 준비 상태도 함께 기록한다.

- 구현 완료 범위
- Git 제품의 branch·HEAD·working tree 상태와 staged/unstaged/untracked 준비 변경 범위. dirty HEAD를 복구 가능한 준비 완료 기준점이라고 부르지 않는다. `/adapt` 전에 이번 작업의 검증된 변경은 상시 승인 commit 등으로 보존하고 준비 상태 전체의 복구 가능성을 확인해야 한다. 범위 밖 변경을 함께 commit하지 않으며 tag는 별도 승인 없이 만들지 않는다.
- 코드 보존·게시 체크포인트의 실제 로컬 경로, 승인 범위, 게시 remote/branch·검증한 commit/remote SHA 또는 미게시 상태·이유·후속 승인 항목. 미게시 변경은 사용자 종료 보고에서도 숨기지 않는다.
- hosted app이면 실제 앱 위치·소유 계정·권한과 확인된 복구 방법·근거. 버전/복원 기능을 추정하지 않으며 미확인이면 위험과 `/adapt` 전 보존 확인 조건을 적는다.
- sponsor별 준비 상태 또는 N/A 이유
- 현장에서 해야 할 일
- deploy/run/reset 방법
- known risks

secret 값은 적지 않는다.

## 발표 초안 제안 시점

핵심 demo의 입력→행동→결과와 보여줄 장면이 잡히면 행사 전에도 `/deck` 초안, 이어 `/pitch` 초안을 준비할 시점과 다음 작업을 선제 제안한다. 자동 실행하지 않는다. 각 command의 필수 입력이 갖춰졌는지 먼저 확인하고, 부족하면 해당 입력을 만드는 작업부터 제안한다. 초안이라는 이유로 필수 입력이나 렌더 QA·실제 리허설 등 완료 계약을 우회하지 않는다.

확인된 공식 심사 기준마다 연결할 demo/evidence 장면과 근거를 제안한다. rubric이 unknown이면 미확인으로 남기고 발명하지 않는다. 실제 미검증 결과는 초안의 evidence 대기 자리 또는 한계로 구분하며 성과·수치를 채워 넣지 않는다. local/mock 근거를 현장·실제 sponsor 결과로 승격하지 않고 현장 검증 후 갱신할 항목을 남긴다. 행사 전 초안은 breadcrumb의 on-site 완료를 뜻하지 않는다.
