## 종료 게시 절차

종료 시 사용자 재승인 없이 상시 승인된 이번 command의 검증된 변경만 게시한다. kit 기록과 제품 repo를 분리하고 각 저장소의 명시 경로·hunk만 stage한 뒤 staged diff를 검수해 commit·push한다(`git add .`/`-A` 금지). 기존 index와 다른 스레드 작업, secret·개인정보·개인사진·권한 없는 원본·생성 캐시는 제외하며 분리할 수 없으면 보류한다. 변경이 없으면 빈 commit을 만들지 않는다. 제한·충돌·실패 시 변경을 보존하고 게시 대기 범위와 이유를 보고한다. 대상 remote branch SHA를 readback해 로컬 commit SHA와 대조하고 종료 보고에 저장소별 SHA·push 상태를 포함한다. tag, reset, force push, branch 생성·삭제, 공개 전환과 앱 복원은 별도 승인이 필요하다. 이 절차는 구현·외부 제출이나 다음 command 실행의 포괄 승인이 아니다.

## 실행 표시

흐름 첫 줄은 Markdown 인용문(`> `)으로 표시하고 코드 블록이나 인라인 코드로 감싸지 않는다. 실제 완료된 command만 굵게, 진행 중과 이후 command는 일반체로 쓴다. 아래는 형식 예시이며 실제 완료 여부는 행사 근거로 확인한다.

> **/init** → **/ideate** → /design (진행 중) → /demo


시작·중간 보고·종료 응답의 첫 줄은 command 단독이 아니라 준비 흐름 breadcrumb로 쓴다. 아래 시작/종료의 단독 command 템플릿은 breadcrumb로 대체하고 행사·범위·산출물·남은 조건은 그 뒤 또는 다음 줄에 보존한다.

전체 행사 흐름: [workflow 계약](../../references/workflow-policy.md)의 prebuild-permitted / on-site-build-only / restricted-preparation 분기를 따른다. /demo criteria → 제작 → /demo verify 순서이며 /replan 내부 init+ideate 조사만 자동실행금지의 명시적 예외다. 현재 사용자의 게시 금지·보호 경로는 종료 게시 절차보다 우선한다.

- 현재 단계와 앞뒤 단계를 포함한 연속 구간을 읽기 좋게 발췌한다. 양 끝에서는 가능한 이웃을 포함한다. 순서는 위치 안내이지 자동 다음 단계 실행 승인이 아니다.
- 굵게는 해당 행사·모드의 실제 완료 근거가 확인된 command에만 쓴다. 현재 단계에는 `(진행 중/선택 대기/초안/부분완료/실패/완료)` 등 실제 상태를 붙인다. 미래 단계는 일반체, unknown·기록 부재·근거 충돌은 `(미확인)`이다. 앞 단계라는 이유나 파일 존재만으로 완료를 추정하지 않는다. N/A는 공식 근거와 적용 이유가 확인된 경우에만 일반체로 표시한다.
- 조건부 예시: init과 ideate의 완료를 실제 확인한 경우에만 `**/init** → **/ideate** → /design (진행 중) → /demo(pre-event)`로 표시한다. 확인 전에는 `/init (미확인) → /ideate (미확인) → /design (진행 중) → /demo(pre-event)`다.
- slash 입력이 없는 자연어 요청도 실제 수행 내용과 입력/산출물 계약으로 단계를 매핑한다. 불명확하면 확인된 구간 또는 전체 흐름 뒤에 `| 현재 단계 확정못함 (미확인)`을 붙이고 확인 질문 후 대기한다. 표시를 생략하거나 임의의 현재 단계를 고르지 않는다.
- 아래 command별 완료 기준을 유지한다. 문서 초안만으로 /design·/prepare를 완료 또는 굵게 표시하지 않는다. 검토완료와 제품 PASS, 초안과 실제 제출은 구분하며 남은 조건과 실제 verdict를 숨기지 않는다.

“다음 작업 진행해줘” 같은 자연어 요청도 최신 대화와 현재 파일을 확인한다. 아래 개별 시작/종료 표시는 breadcrumb 뒤에 둘 부가정보와 상태 기준이며 첫 줄의 흐름을 대체하지 않는다. 미확정 상태도 위 breadcrumb 규칙으로 표시하고, 확인할 수 없으면 질문하고 대기로 종료한다. 단계를 지어내거나 완료로 승격하지 않는다. 표시만으로 작업 승인이나 다음 단계 실행 권한이 생기지 않는다. 흐름 breadcrumb를 생략한 응답·보고는 완료로 처리하지 않으며, 자연어 요청도 매핑을 생략하지 않는다.

`AGENTS.md`의 현재 해커톤 workspace 선택과 Command 입출력, 제품 위치와 복구 경계를 따른다. 시작에 `/design · 시작 | 행사 slug(미확정이면 행사 미확정) | 이번 작업 범위`, 종료에 `/design · 실제 상태 | 행사 slug | 산출물 또는 없음 | 남은 승인/다음 단계`를 표시한다. 문서만 작성했으면 초안 작성 / 구현 대기, 본문의 실제 UI 반영과 screenshot 확인까지 충족했을 때만 완료다. 일부만 마쳤으면 부분완료, 입력·승인 부족이면 대기, 작업 실패면 실패다. 질문으로 멈출 때도 종료를 표시하며 도구 호출마다 반복하지 않는다. 다음 command는 안내만 하고 승인 없이 자동 실행하지 않는다.

선택한 제품 위치(Git 저장소 또는 소유 계정의 hosted app)와 현재 행사 workspace를 읽는다. build_policy의 design/prompt/data 등 행위별 사전 허용을 먼저 확인한다. 위치가 미정이어도 공식 허용·사용자 승인된 초안은 가능하지만 `/design` 완료는 아니다. 금지·미확인 사전설계를 초안이라는 이유로 진행하지 않는다.

`/design` 시작 조건에 `hackathon.yaml`의 `product.name` 확정을 포함한다. 미확정이면 임시 코드명으로 초안 단계는 진행할 수 있으나 완료는 아니다. 작업 중 이름이 바뀌면 영향 범위(제품 저장소/화면/문서/덱/제출 폼 중 해당 항목)를 종료 보고에 자동으로 남기고 `/adapt`·`/retro`에서 추적한다. 저장소 이름 규칙은 `AGENTS.md`를 따르며 과거 행사의 일괄 rename은 하지 않는다.

목표는 moodboard를 만드는 것이 아니다. 실제 제품 UI와 deck에 적용 가능한 디자인 결정을 내리고 구현하는 것이다.

## 사전설계 검토와 UI 구현의 분리

[사전 준비 완료 기준](../../references/pre-event-readiness.md)을 읽고 제품 명세의 사용자·입력·행동·산출물과 고정/가변 경계를 먼저 확인한다. 빈칸이 핵심 경험을 바꾸면 이를 먼저 정리하며 임의 예제로 확정하지 않는다. `/design`은 UX와 시각 설계이며 시스템 구조 문서만으로 대신하지 않는다.

planning/design이 허용된 현장 제작 전용 행사에서도 코드 없는 화면·상태 설계를 구체화하고 사용자 검토를 받는다. 허용된 와이어프레임·이미지·스토리보드 등으로 진입 → 입력 → 역할·목표 → 실제 버튼/입력 조작 → 상태 전이 → 완료를 보여준다. loading, 잘못된 입력, 빈 결과, 정보 누락·모순, 모델·인프라 오류와 복구를 필요한 범위에서 정하고 안내가 실제 업무 상태와 일치하도록 설계한다.

검토할 산출물을 전달하고 버전·사용자 검토/승인·미해결 쟁점과 walkthrough의 빈칸 해소 기록을 `design.md`에 남긴다. 레퍼런스 동의만으로 이 검토를 완료하지 않는다. 허용된 사전설계를 합의했으면 `사전설계 검토완료 · 제품 UI 미구현`으로 기록할 수 있으나 실제 UI 적용·screenshot을 요구하는 본문 `/design` 구현 완료나 굵은 완료 표시로 승격하지 않는다. 사전설계 자체가 금지·미확인이면 그 제한을 남기며 초안·HTML 목업이라는 이유로 우회하지 않는다.

## 1. 먼저 확인

- 기존 제품의 design system
- 현재 UI screenshot
- demo에서 보여줄 화면
- projector / screen share 환경
- 제품 logo / brand가 있으면 그 자산
- 제공된 visual reference
- deck과 제품을 같은 시각 언어로 가져갈지 여부

이미 제공된 reference를 먼저 확인한다. 없거나 불명확하면 선호하는 사이트/앱/이미지/무드 레퍼런스가 있는지 한 번 묻되, 이미 제공한 레퍼런스를 다시 요구하지 않는다. 레퍼런스에서 무엇을 가져오고 무엇을 피할지 짧게 확인한다. 레퍼런스가 없으면 기존 디자인 체계 또는 제안 시안으로 진행할 수 있으며, 레퍼런스 확보는 필수 gate가 아니다. 이미지나 링크를 볼 수 없다면 그 한계를 밝히고 본 척하지 않는다.

## 2. Demo 화면 선택

심사위원이 실제로 볼 화면을 먼저 정한다.

각 화면에 대해 적는다.

- 화면 목적
- 사용자가 하는 행동
- 반드시 읽혀야 하는 결과
- loading / success / failure / error
- screenshot으로 쓸 영역

demo에 안 나오는 화면을 우선해서 디자인하지 않는다.

실제 사용자의 업무 흐름에서 첫 입력과 마지막 전달을 데모 화면 안에 둔다. 예를 들어 해상 실종이면 신고 원문 입력에서 시작해 출동팀·상황실 공유 문구로 끝난다. 계산 결과 화면만 있으면 "누가 이걸 쓰는지"가 보이지 않는다.

## 3. Visual direction

기존 제품이 있으면 그 체계를 유지한다.

새 제품이면 최소한 아래를 정한다.

- background / surface
- typography hierarchy
- accent roles
- spacing scale
- radius / border
- input / button / card
- status colors
- code / log / number treatment
- icon style
- screenshot framing

색 이름보다 역할을 정의한다.

사용자가 시각 예시를 요청하면 실제로 열어볼 수 있는 입력과 결과를 파일 경로나 URL로 전달한다. 요청된 사진의 전후 비교는 해당 사진의 입력·결과로 보여주며 설명이나 무관한 샘플로 대체하지 않는다. 만들 수 없으면 그 한계와 미제공 상태를 밝힌다. 결과가 수동 제작인지, 목업인지, 자동 처리인지, 실제 제품 실행인지 구분하고 사용 경로를 적는다. 자동 처리 예시도 실제 제품 경로에서 실행하지 않았다면 제품 실행 증거로 부르지 않는다. 외부 전송·유료 호출·제품 수정은 기존 승인 경계를 따른다.

시각 승인은 외형·흐름에 대한 승인이지 기술 검증 통과나 구현 승인이 아니다. 시각 예시를 demo 품질·기능 검증의 대체 근거로 쓰지 않으며, 검증 주장은 기존 demo contract의 독립 기준과 실제 실행 evidence를 따른다.

## 4. 상태 디자인

happy path만 만들지 않는다.

최소한 필요한 상태를 구현한다.

- idle
- loading
- success
- failure
- empty
- infrastructure error
- unverified: 제품이 사용자에게 검증되지 않은 판정을 제공하는 경우에만 필요한 상태

사용자에게 판정을 제공한다면 제품 verdict와 infra/model error, unverified가 같은 시각 상태로 보이지 않게 한다. CI comment처럼 UI가 아닌 surface도 같다. 내부 demo 검증의 UNVERIFIED를 모든 제품 UI에 강제하지 않는다. 편집·생성 제품은 해당 동작의 실패·불확실성을 표현하되 범위 밖 판정 기능을 추가하지 않는다.

## 5. Demo readability

projector와 screen share를 기준으로 본다.

- 핵심 결과가 한눈에 보임
- 작은 text에 의존하지 않음
- contrast 충분
- 중요한 값은 fold 위
- debug 정보가 핵심 결과를 밀어내지 않음
- secret, token, 개인 정보 없음
- 데모 첫 화면에 핵심 결과는 세 개 이내로 두고 나머지는 접어 둔다. 사용자가 꼭 보고 싶다고 한 장면은 위로 올린다.

레퍼런스나 연구를 찾기 전에 무엇의 근거인지(UI/UX, 도메인 사실, 심사)를 먼저 적고 그 범위만 찾는다. UI/UX 근거를 찾으라는 요청에 도메인 설문을 찾아 오면 다시 찾아야 한다.

## 6. 구현

결정은 `workspace/<event-slug>/design.md`에 남긴다. 실제 UI 구현 전에 `/demo criteria`의 독립 기준과 시각 승인을 확인한다. 실제 UI 구현은 공식 제작 시간·사용자 작업 승인·제품 위치와 소유 권한을 확인한 뒤에만 진행하고 `AGENTS.md`의 제품 위치와 복구 경계를 따른다. 시각 승인은 구현 승인이 아니며 제품 범위 승인이나 사전 제작 가능 가정을 구현 권한으로 확대하지 않는다.

실제 제품 구현에 들어가기 전에 `/prepare` 본문의 코드 보존·게시 체크포인트를 적용한다(`/prepare` 자동 실행이 아니다). 해커톤의 별도 제한 안내가 없는 한 제품 선택 후 첫 구현 전에 적합한 기존 repo를 재사용하거나 확인된 사용자 계정에 새 비공개 repo를 확보한다. 이름·소유·충돌·작업 범위가 모호하면 먼저 확인하고 후보 탐색 단계에서 후보마다 repo를 만들지 않는다. repo/remote/owner/visibility/branch/HEAD/dirty와 기존 변경을 확인·보존한다. hosted app도 companion repo를 확보하되 실제 제공되는 내보내기만 보관하고, 내보내기가 불가능하면 승인된 지시서·설정·검증·복구 기록만 남기며 전체 소스를 확보했다고 주장하지 않는다. 앱 자체의 소유·권한·복구 경계는 별도로 확인한다. 검증된 이번 작업의 일반 commit·push는 종료 게시 절차의 상시 승인을 적용하고 게시 결과 또는 게시 대기 이유를 `design.md` 및 사용자 보고에 남긴다. 이 정책은 제품 구현의 포괄 승인이나 사전 구현 금지·공개·제출 규칙의 예외가 아니다.

`/design` 완료를 주장하려면 demo 핵심 화면이 실제 UI에 반영되어 있어야 한다. 규칙·승인·위치가 미확인이라 초안까지만 진행했다면 그 범위와 남은 조건을 기록하고 완료로 처리하지 않는다. 현장 제작만 허용되면 사전 UI 구현을 요구하지 않는다.
