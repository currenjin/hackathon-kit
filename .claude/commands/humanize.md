## 종료 게시 절차

종료 시 사용자 재승인 없이 상시 승인된 이번 command의 검증된 변경만 게시한다. kit 기록과 제품 repo를 분리하고 각 저장소의 명시 경로·hunk만 stage한 뒤 staged diff를 검수해 commit·push한다(`git add .`/`-A` 금지). 기존 index와 다른 스레드 작업, secret·개인정보·개인사진·권한 없는 원본·생성 캐시는 제외하며 분리할 수 없으면 보류한다. 변경이 없으면 빈 commit을 만들지 않는다. 제한·충돌·실패 시 변경을 보존하고 게시 대기 범위와 이유를 보고한다. 대상 remote branch SHA를 readback해 로컬 commit SHA와 대조하고 종료 보고에 저장소별 SHA·push 상태를 포함한다. tag, reset, force push, branch 생성·삭제, 공개 전환과 앱 복원은 별도 승인이 필요하다. 이 절차는 구현·외부 제출이나 다음 command 실행의 포괄 승인이 아니다.

## 실행 표시

흐름 첫 줄은 Markdown 인용문(`> `)으로 표시하고 코드 블록이나 인라인 코드로 감싸지 않는다. 실제 완료된 command만 굵게, 진행 중과 이후 command는 일반체로 쓴다. 아래는 형식 예시이며 실제 완료 여부는 행사 근거로 확인한다.

> **/init** → **/ideate** → /design (진행 중) → /demo


시작·중간 보고·종료 응답의 첫 줄에 준비 흐름 breadcrumb와 보조 command의 실제 대상을 표시한다. 아래 시작/종료의 단독 command 템플릿 대신 `행사 흐름 발췌 | /humanize (실제 상태) | 대상 문서 경로 또는 제공된 글`을 쓰고 나머지 범위·결과·남은 조건은 그 뒤 또는 다음 줄에 보존한다.

전체 행사 흐름: [workflow 계약](../../references/workflow-policy.md)의 prebuild-permitted / on-site-build-only / restricted-preparation 분기를 따른다. /demo criteria → 제작 → /demo verify 순서이며 /replan 내부 init+ideate 조사만 자동실행금지의 명시적 예외다. 현재 사용자의 게시 금지·보호 경로는 종료 게시 절차보다 우선한다.

- decide/humanize는 보조 command이므로 단계 순서에 억지로 편입하지 않는다. 현재 행사 단계가 확인되면 그 단계와 앞뒤의 연속 구간을 발췌하고 보조 작업을 함께 표시한다. 행사와 무관한 글이면 `행사 흐름 해당 없음 | /humanize (실제 상태) | 대상 문서`, 관련 여부나 현재 단계가 불명확하면 `행사 흐름 미확인 | 현재 단계 확정못함 | /humanize (실제 상태) | 대상 문서`로 쓴다. 행사 선택을 강요하지 않는다.
- 굵게는 해당 행사·모드 또는 보조 작업의 실제 완료 근거가 확인된 command에만 쓴다. 현재 단계에는 `(진행 중/선택 대기/초안/부분완료/실패/완료)` 등 실제 상태를 붙이고 미래 단계는 일반체로 쓴다. unknown·기록 부재·근거 충돌은 `(미확인)`이며 앞 단계나 파일 존재만으로 완료를 추정하지 않는다. N/A는 공식 근거와 적용 이유가 확인된 경우에만 일반체로 표시한다.
- slash 입력이 없는 자연어 요청도 실제 수행 내용과 입력/산출물 계약으로 매핑한다. 단계가 불명확하면 위의 확정못함 표시와 확인 질문 후 대기로 종료하며 표시를 생략하지 않는다. 순서는 위치 안내이지 자동 다음 단계 실행 승인이 아니다.
- 문서 초안만으로 /design·/prepare를 완료 또는 굵게 표시하지 않는다. /humanize 완료는 문체 수정과 사실·구조 보존 확인이며 대상 문서가 속한 행사 단계 완료로 전파하지 않는다. 아래의 상태 의미와 승인 경계를 유지한다.

“다음 작업 진행해줘” 같은 자연어 요청도 최신 대화와 현재 파일을 확인한다. 아래 개별 시작/종료 표시는 breadcrumb 뒤에 둘 부가정보와 상태 기준이며 첫 줄의 흐름을 대체하지 않는다. 미확정 상태도 위 breadcrumb 규칙으로 표시하고, 확인할 수 없으면 질문하고 대기로 종료한다. 단계를 지어내거나 완료로 승격하지 않는다. 표시만으로 작업 승인이나 다음 단계 실행 권한이 생기지 않는다. 흐름 breadcrumb를 생략한 응답·보고는 완료로 처리하지 않으며, 자연어 요청도 매핑을 생략하지 않는다.

`AGENTS.md`의 현재 해커톤 workspace 선택 예외와 소유 경계를 따른다. 행사 선택을 강요하지 않고 대상 문서 경로 또는 제공된 글을 표시한다. 시작에 `/humanize · 시작 | 대상 문서 | 이번 수정 범위`, 종료에 `/humanize · 실제 상태 | 대상 문서 | 수정 결과 또는 없음 | 남은 확인/다음 단계`를 표시한다. 문체 수정과 사실·구조 보존 확인을 마쳐야 완료이며 제품 구현 완료를 뜻하지 않는다. 일부만 마쳤으면 부분완료, 대상·입력이 부족하면 대기, 작업 실패면 실패다. 질문으로 멈출 때도 종료를 표시하며 도구 호출마다 반복하지 않는다. 다음 command는 안내만 하고 승인 없이 자동 실행하지 않는다.

대상 문서의 글투만 다듬는다. 사실, 수치, 코드, 링크, 표, 불릿, 헤딩 구조는 바꾸지 않는다. 행사 자료면 build_policy의 해당 행위 허용을 확인하며 문체 수정으로 규칙 금지·unknown을 우회하지 않는다. historical/재검수 대기와 oracle 한계를 지우거나 과거 evidence를 최신 출품 성과로 바꾸지 않는다.

아래 규칙을 순서대로 적용한다.

1. `.claude/rules/writing/common.md`
2. `.claude/rules/writing/ko.md`

특히 아래를 찾는다.

- 번역투
- em-dash
- 과한 볼드
- 정형 라벨
- 습관적인 헤지
- 같은 어미 반복
- 추상적인 범주어
- 비유적 기술 표현
- `~하는 것` 명사화 반복

deck이나 pitch라면 문장을 더 짧게 만들 수 있지만 의미를 추가하지 않는다. 변경 뒤 demo 숫자와 고유명사가 그대로인지 확인한다.

## 문체 수정 뒤 사실 범위 재검수

문체를 다듬은 뒤, 렌더·게시 전에 [사실 범위 재검수](../../references/claim-scope-check.md)를 적용한다. 수치·조건·한계와 포괄 표현을 원문·고정 expected·실행 evidence에 대조하고, 미확인과 승인 범위를 보존한다.
