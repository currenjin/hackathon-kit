## 실행 범위와 표시

`AGENTS.md`의 현재 workspace 선택, 소유·복구 경계, 언어·작성 규칙과 종료 게시 절차를 따른다. 이 command는 행사 전·현장 모두 사용할 수 있는 재계획 분기이며 매번 거쳐야 하는 선형 단계가 아니다.

시작·중간·종료 응답의 첫 줄은 Markdown 인용문으로 흐름 breadcrumb를 표시한다. 코드 블록·인라인 코드로 감싸지 않고 실제 완료 근거가 있는 단계만 굵게 쓴다. 현재 단계의 실제 상태와 다음 단계의 시작 조건을 구분한다. 자연어의 “규칙 바뀌었으니 준비 다시 정리해줘”도 `/replan`으로 매핑한다. 생략한 보고는 완료로 처리하지 않는다. 다음은 형식 예시이며 행사 완료 사실이 아니다.

> /replan [/init 재확인 (진행 중) → /ideate 전체 재평가 (대기)] → 사용자 결정 대기

[workflow 계약](../../references/workflow-policy.md)의 prebuild-permitted / on-site-build-only / restricted-preparation 분기를 적용한다. 현재 사용자의 게시 금지·보호 경로는 종료 게시 절차보다 우선한다.

`/replan` 실행 승인은 내부 `/init` 재확인과 `/ideate` 전체 재평가의 조사·기록·recommendation 실제 수행까지 포함한다. 이는 하위 command 자동실행금지 기본규칙의 명시적 예외이며 init+ideate 조사 범위에만 한정한다. 두 command를 다음 작업으로 안내만 하고 종료하지 않는다. 제품 선택·명칭·sponsor 채택은 사용자 결정이다. 제품 코드·앱 수정, 새 제품 구현, 유료 호출, 계정·저장소 생성, branch 생성·삭제, 공개 전환, 배포·제출, 원본·이력 삭제, 그 밖의 command 자동 실행은 승인하지 않는다. 행사 규칙의 금지는 사용자 승인으로 해제할 수 없다.

## 입력과 산출물

- 필수: 현재 행사를 확정할 수 있는 `hackathon.yaml`, 새 안내·변경 전제 또는 재확인 요청. 행사 URL·날짜로 대상을 확정하며 최근 폴더를 임의로 고르지 않는다. 신규 행사라면 `/init`을 안내한다.
- 읽기: 기존 공식 출처·확인 기록, 선택 이유, `ideation.md`, `design.md`, `preparation.md`, `adaptation.md`, preflight 기록, 실제 demo contract, deck·pitch·submission 보고와 현재 기준 버전(각각 있으면). `demo_contract`는 AGENTS의 탐색 순서를 지키며 고정 파일명을 가정하지 않는다. 제품의 작성 시점·상태 판단이 필요하면 해당 저장소의 로그·상태를 읽기만 한다.
- 쓰기: `replan.md`, `hackathon.yaml`, 기존 sources/notes의 변경 이력, `ideation.md`의 전체 재평가·추천 및 영향받은 기존 준비 문서의 현재 상태·제약·재검수 표시. 과거 선택·근거를 보존한다.
- 기록이 없으면 미확인으로 남긴다. `preparation.md`나 기존 demo contract가 없어도 재계획은 가능하며 구현·실행 완료 기록을 만들어 채우지 않는다. 다른 command의 필수 입력 계약을 우회하지 않는다.
- 다른 행사 workspace, 제품 코드·과거 evidence·기존 덱/대본 파일, 공통 kit 규칙은 수정하지 않는다. 제품 README 정정 등 제품 저장소 변경도 별도 승인 범위다.

## 1. init 재확인을 실제 수행한다

[init](init.md)의 재확인 모드와 조사 절차 전체를 수행한다. 동일 URL·날짜의 현재 workspace를 유지하고 빈칸만 채우는 규칙의 예외에 따라 변경값·이전값·출처 이력을 보존한다. 새 workspace 생성이나 일괄 migration은 하지 않는다. 아래 규칙 조사는 init의 수행 항목이며 별도 실행 승인을 다시 요구하지 않는다.

1. 공식 행사 페이지, 최종 안내, 운영진 정정·질의 답변을 직접 읽는다. 새 안내의 모든 관련 탭·첨부를 확인한다. 링크 목록·검색 snippet·기존 요약만으로 원문 전체 확인을 주장하지 않는다. 접근 불가·로그인·누락 첨부는 미확인과 질문으로 남긴다. 비밀번호나 API key를 요구하지 않는다.
2. 원문 위치(URL·탭·절), 확인 시각과 시간대, 필요한 짧은 인용·요약을 기록한다. 개인정보·계정·키·비공개 원문 전체는 저장하거나 게시하지 않는다.
3. 사전 제작·기존 코드·라이브러리/스타터·아이디어/설계/프롬프트/데이터 사전 준비, 제작 시작·종료, 필수·금지 기술, 참가·수상 자격, 트랙·심사, 언어, 배포, 제출물·공개 범위·마감, 발표·Q&A, 계정 만료·백업 조건을 각각 확인한다. 코드만 안 쓰면 다른 모든 준비가 허용된다고 추론하지 않는다.
4. 이전 조건 → 새 조건 → 출처 → 확정/변경/미확인/충돌 → 영향 범위를 적는다. 상위 규정과의 관계·동일 회차의 최신 공식 정정 여부를 확인한다. 늦은 안내라는 이유만으로 상위 규정을 무효화하지 말고 충돌은 운영진 질문으로 남긴다. 사용자 경험·사용자 확인·공식 확인을 구분한다.
5. 미확인은 허용이 아니다. 명시된 허용 범위의 저위험 준비만 진행하며 출품용 구현을 보류한다. 미확인 사항을 거짓·불허로 확정하지도 않는다.

## 2. ideate 전체 재평가와 영향 판정을 실제 수행한다

[ideate](ideate.md)의 제품·과거 참가·수상작·일반 출품작 조사와 전체 비교 절차를 실제 수행한다. 새 공식 트랙·필수 기술·심사 기준으로 기존 아이디어 유지 / 수정 / 새 후보를 비교하고 코드 재사용 자격은 별도로 판단한다. 이전 선택과 근거는 보존하되 현재 상태는 `재평가 대기`로 표시한다. recommendation·근거·가장 강한 반론·철회 조건을 ideation.md에 기록하며 사용자 승인 없이 선택을 덮어쓰지 않는다.

규칙/출처 미확인이나 planning 금지로 새 후보 작성이 막히면 그 하위항목은 부분완료/보류다. 가능한 기존 기록 비교·자격 검토 등 비차단 검토는 수행하고 필요한 운영진 질문을 남긴다. 허용 추론이나 전체 재평가 수행 사실의 허위 보고는 금지한다.

준비 모드는 다음 중 근거가 있는 하나로 기록한다. 세부 행위별 허용 여부가 모드 이름보다 우선한다.

- `restricted-preparation`: 제작 허용 범위 미확인. 출품용 구현 없이 확인된 준비만 진행.
- `prebuild-permitted`: 공식적으로 확인한 사전 제작 범위 안에서만 준비. 실제 구현 승인은 별도.
- `on-site-build-only`: 사전 제작 금지. 허용된 도구·학습 준비와 현장 신규 제작 계획으로 전환. 행사 전이라면 구현은 대기하고, 현장이면 공식 시작 시점과 사용자 작업 승인을 각각 확인.

아이디어·설계·제품 코드·입력/expected/fixture·데모 evidence·덱·대본·제출 자료·repo 공개 상태·기기/계정 준비 각각을 인벤토리로 만든다. 각 항목에 경로/현재 버전, 작성 시점(검증 불가 시 미확인), 관련 조건, 판정, 조치, 다음 검증을 기록한다.

판정은 `유지 / 수정 필요 / 연습용 전환 / 출품 사용 불가 / 확인 대기`다. 기존 제작이 금지되면 앱·ZIP·그 결과로 만든 덱을 출품용에서 제외하고 학습 이력으로 보존한다. 아이디어 논의까지 금지됐다고 확대 해석하거나 반대로 같은 프로젝트의 현장 재작성이 자동 허용된다고 주장하지 않는다. 필요한 경우 운영진 확인 후 후보를 다시 선택하도록 제안한다.

완성 코드를 스타터라고 재분류하거나 이름·새 repo·commit 시각을 바꿔 사전 제작 사실을 숨기지 않는다. 기존 테스트 PASS, stub/local/mock, 과거 배포 성공을 현장 신규 출품물의 실행 증거로 재사용하지 않는다. 기존 expected의 출처와 고정 이력은 유지하며 새 출품 contract가 필요하면 `/demo`의 별도 작업으로 제안한다.

## 3. 유효하지 않은 완료 판정을 실제로 해제한다

1. 조건 변경에 영향을 받는 단계만 현재 완료 판정을 해제한다. 과거 실행 사실은 삭제하지 않고 `historical / 현재 출품 기준 아님 / 재검수 대기`를 근거·이전값·새값과 함께 남긴다. 영향을 받지 않는 검증·설치는 유지한다. 모든 단계를 일괄 초기화하지 않는다.
2. 기존 상태 필드가 있으면 그 스키마 안에서 갱신한다. 필드가 없으면 임의 완료 필드·일괄 migration 대신 `hackathon.yaml` notes와 `replan.md`에 현재 verdict 및 재개 조건을 명시한다. 새로 확인한 공식 필수 조건은 적합한 기존 필드에 반영하되 제품명·채택·제외를 사용자 대신 결정하지 않는다.
3. 발표 조건 또는 출품 근거가 바뀌면 `presentation.status: dirty`를 기록한다. 현재 기준 덱이 무효라면 `presentation.review.active_version: null`, `status: superseded`, `reviewed_at: null`로 두고 이전 active 경로를 `superseded_versions`에 중복 없이 보존한다. 이전 승인 시점은 `replan.md` 이력에 보존한다. 실제 검토 중인 대체본이 있으면 경로와 상태를 기록하되 사용자 승인 없이 active로 승격하지 않는다.
4. 이미 실제 제출한 사실은 submitted 또는 submitted_user_confirmed에서 draft로 되돌리지 않는다. 사용자 보고와 접수 직접 검증의 근거 수준은 보존한다. 접수 사실과 현재 적합성·정정 필요를 분리하고 철회·재제출은 승인 대기로 남긴다. 실제 GitHub 공개 상태·배포 상태도 메타데이터만 바꿔 취소됐다고 주장하지 않는다.
5. 과거 파일은 보존하고 새 현장 산출물 경로를 분리한다. 현재 기준 문서 상단에는 `replan.md` 링크와 적용 여부를 표시해 과거 보고가 최신 완료로 오인되지 않게 한다.

## 4. 실제로 실행 가능한 준비 계획으로 바꾼다

`replan.md`에 다음을 구분한다.

- 지금 가능한 준비: 공식 허용 근거가 있는 도구 설치·문서 학습·현장 절차 확인 등. 단순 설치 확인은 지참 기기와 현재 agent host를 구분한다.
- 확인 전 보류: 운영진에게 묻는 구체 질문, 결정권자, 해제 조건. 아이디어·제품별 설계·프롬프트·데이터·발표자료 사전 작성은 개별 허용 확인 없이 허용 목록에 넣지 않는다.
- 공식 시작 이후 새로 할 작업: 입력 → 핵심 동작 → 실제 결과의 최소 흐름, 필수 AI/Cloud/제출, 증거 수집·백업 순서.
- 시간 예산: 실제 제작 가능 시간을 근거로 계획하고 행사 전체 길이·등록 마감·제출 마감·발표시간을 혼동하지 않는다. 합계는 도구로 계산한다. 미확인 시간이면 가정과 재계산 조건을 표시한다.
- 실패 시 축소: 필수 요건은 보존하며 기능을 줄인다. mock/local fallback은 시연 보조이지 필수 AI·배포 성공의 대체가 아니다.
- 다음 command와 시작 조건: 내부 ideate 재평가 결과에 대한 사용자 결정, 허용된 `/demo criteria` → `/design`·`/prepare`, 필요 시 계정 연결 `/adapt`, `/demo verify`의 실제 증거 후 `/deck`·`/pitch`, 최종 `/preflight` 등. 현장 신규 구현은 승인된 `/design`·`/prepare` 범위이며 `/adapt` 연결 수정으로 위장하지 않는다. 내부 조사 외 다음 command는 자동 실행하지 않는다.

`/adapt`는 구체 조건 기록·실제 환경 연결을 담당한다. 전체 출품 자격·제품 방향·완료 상태를 바꿀 변화는 `/replan`에서 먼저 재편한다. 재계획 문서 완료는 구현·발표·출품 준비 완료가 아니다.

## 5. 검증과 종료

- 변경 전 dirty/index를 확인하고 다른 스레드 변경을 보존한다. 같은 필드의 동시 변경은 덮어쓰지 않고 충돌로 보고한다.
- 변경 YAML 파싱, 상대 경로·링크 유효성, 기존 필드·evidence 보존을 검사한다. 판정 목록과 변경된 문서·현재 기준이 서로 일치하는지 확인한다.
- 금지된 기존 산출물이 현재 active로 남지 않는지, 영향받은 과거 PASS가 최신 PASS로 읽히지 않는지, 미확인이 허용·실행 성공으로 승격되지 않았는지 점검한다.
- 원문 접근 불가·핵심 규칙 충돌이면 재계획은 부분완료/확인 대기로 종료한다. 확인된 금지와 그 안전 조치는 즉시 기록할 수 있지만 미확인 해결을 주장하지 않는다.
- 종료에는 init 재확인과 ideate 전체 재평가 각각의 실제 수행·미수행 범위, 변경 규칙, 유지/철회된 산출물·상태, recommendation, 사용자 결정 대기, 다음 command와 시작 조건을 보고한다. 재계획 완료는 제품 선택·구현 완료가 아니다.

종료 시 이번 command의 검증된 행사 기록만 상시 승인에 따라 commit·push한다. kit와 제품 repo를 분리하고 명시 경로·hunk만 stage한다(`git add .`/`-A` 금지). 다른 스레드 변경·secret·개인정보·권한 없는 원본·캐시는 제외하고 분리 불가 시 보류한다. 빈 commit은 만들지 않는다. staged diff 검수 후 게시하고 원격 branch SHA를 로컬 commit과 대조한다. 실패 시 작업을 보존하고 게시 대기로 보고한다. 이 절차는 제품 변경·외부 제출·다음 command의 실행 승인이 아니다.
