## 종료 게시 절차

종료 시 사용자 재승인 없이 상시 승인된 이번 command의 검증된 변경만 게시한다. kit 기록과 제품 repo를 분리하고 각 저장소의 명시 경로·hunk만 stage한 뒤 staged diff를 검수해 commit·push한다(`git add .`/`-A` 금지). 기존 index와 다른 스레드 작업, secret·개인정보·개인사진·권한 없는 원본·생성 캐시는 제외하며 분리할 수 없으면 보류한다. 변경이 없으면 빈 commit을 만들지 않는다. 제한·충돌·실패 시 변경을 보존하고 게시 대기 범위와 이유를 보고한다. 대상 remote branch SHA를 readback해 로컬 commit SHA와 대조하고 종료 보고에 저장소별 SHA·push 상태를 포함한다. tag, reset, force push, branch 생성·삭제, 공개 전환과 앱 복원은 별도 승인이 필요하다. 이 절차는 구현·외부 제출이나 다음 command 실행의 포괄 승인이 아니다.

## 실행 표시

흐름 첫 줄은 Markdown 인용문(`> `)으로 표시하고 코드 블록이나 인라인 코드로 감싸지 않는다. 실제 완료된 command만 굵게, 진행 중과 이후 command는 일반체로 쓴다. 아래는 형식 예시이며 실제 완료 여부는 행사 근거로 확인한다.

> **/init** → **/ideate** → /design (진행 중) → /demo


시작·중간 보고·종료 응답의 첫 줄은 command 단독이 아니라 준비 흐름 breadcrumb로 쓴다. 아래 시작/종료의 단독 command 템플릿은 breadcrumb로 대체하고 행사·범위·산출물·남은 조건은 그 뒤 또는 다음 줄에 보존한다.

전체 행사 흐름: [workflow 계약](../../references/workflow-policy.md)의 prebuild-permitted / on-site-build-only / restricted-preparation 분기를 따른다. /demo criteria → 제작 → /demo verify 순서이며 /replan 내부 init+ideate 조사만 자동실행금지의 명시적 예외다. 현재 사용자의 게시 금지·보호 경로는 종료 게시 절차보다 우선한다.

- 현재 단계와 앞뒤 단계를 포함한 연속 구간을 읽기 좋게 발췌한다. 양 끝에서는 가능한 이웃을 포함한다. 순서는 위치 안내이지 자동 다음 단계 실행 승인이 아니다.
- 굵게는 해당 행사·모드의 실제 완료 근거가 확인된 command에만 쓴다. 현재 단계에는 `(진행 중/선택 대기/초안/부분완료/실패/완료)` 등 실제 상태를 붙인다. 미래 단계는 일반체, unknown·기록 부재·근거 충돌은 `(미확인)`이다. 앞 단계라는 이유나 파일 존재만으로 완료를 추정하지 않는다. N/A는 공식 근거와 적용 이유가 확인된 경우에만 일반체로 표시한다.
- 조건부 예시: init과 ideate의 완료를 실제 확인한 경우에만 `**/init** → **/ideate** → /design (진행 중) → /demo(pre-event)`로 표시한다. 확인 전에는 `/init (미확인) → /ideate (미확인) → /design (진행 중) → /demo(pre-event)`다.
- slash 입력이 없는 자연어 요청도 실제 수행 내용과 입력/산출물 계약으로 단계를 매핑한다. 불명확하면 확인된 구간 또는 전체 흐름 뒤에 `| 현재 단계 확정못함 (미확인)`을 붙이고 확인 질문 후 대기한다. 표시를 생략하거나 임의의 현재 단계를 고르지 않는다.
- 아래 command별 완료 기준을 유지한다. 문서 초안만으로 /design·/prepare를 완료 또는 굵게 표시하지 않는다. 검토완료와 제품 PASS, 초안과 실제 제출은 구분하며 남은 조건과 실제 verdict를 숨기지 않는다.

“다음 작업 진행해줘” 같은 자연어 요청도 최신 대화와 현재 파일을 확인한다. 아래 개별 시작/종료 표시는 breadcrumb 뒤에 둘 부가정보와 상태 기준이며 첫 줄의 흐름을 대체하지 않는다. 미확정 상태도 위 breadcrumb 규칙으로 표시하고, 확인할 수 없으면 질문하고 대기로 종료한다. 단계를 지어내거나 완료로 승격하지 않는다. 표시만으로 작업 승인이나 다음 단계 실행 권한이 생기지 않는다. 흐름 breadcrumb를 생략한 응답·보고는 완료로 처리하지 않으며, 자연어 요청도 매핑을 생략하지 않는다.

`AGENTS.md`의 현재 해커톤 workspace 선택과 Command 입출력, 사전 제작·작업 승인 경계를 따른다. 시작에 `/ideate · 시작 | 행사 slug(미확정이면 행사 미확정) | 이번 작업 범위`, 종료에 `/ideate · 실제 상태 | 행사 slug | 비교 결과/선택 기록 또는 없음 | 남은 결정/다음 단계`를 표시한다. 선택 전에는 검토완료 / 선택 대기, 사용자 선택 기록 후에는 완료로 쓰되 구현 승인으로 보지 않는다. 일부만 마쳤으면 부분완료, 입력·승인 부족이면 대기, 작업 실패면 실패다. 질문으로 멈출 때도 종료를 표시하며 도구 호출마다 반복하지 않는다. 다음 command는 안내만 하고 승인 없이 자동 실행하지 않는다.

현재 행사 workspace의 `hackathon.yaml`, `products.md`, `references/my-hackathons.md`, `references/winners.md`, `references/submissions.md`를 읽는다.

각 파일은 목적을 구분해서 사용한다.

- `references/my-hackathons.md`: 내가 실제로 했던 행사와 다시 볼 링크
- `references/winners.md`: 수상작의 문제 정의, demo, sponsor 활용 패턴
- `references/submissions.md`: 전체 출품 경향과 아이디어 분포

목표는 새 아이디어를 많이 만드는 것이 아니라 이번 행사에 맞는 제품 방향을 고르는 것이다.

## 참고 자료 선택

[자료와 실행 기록 인계](../../references/delivery-handoffs.md)와 [조건부 스타터 목록](../../references/starter-references.md)은 필요한 경우만 읽는다. [합성 작성 예시](../../examples/synthetic-handoff.md)는 기록 형식 참고이지 실제 수요·공식 기준·실행 evidence가 아니다. 기존 명세 경로를 재사용하고 공식 심사 기준 대신 외부 점수표를 넣지 않는다. starter 채택·설치·제품 구현은 별도 승인 범위다.

## 선택 이후 제품 명세 인계

[사전 준비 완료 기준](../../references/pre-event-readiness.md)을 읽고 방향 선택과 제품 명세 완료를 구분한다. 선택한 안의 사용자·상황·구체 입력·실제 행동·최종 산출물, 지원/제외 범위, 고정/가변 기능, AI/코드/사람 책임을 `ideation.md` 또는 연결된 명세에 남긴다. 명세 작성은 planning 허용과 작업 승인 범위에서만 한다.

빈칸은 가정·미정으로 표시하고 `/design` 전에 정할 제품 질문으로 인계한다. 사용자 선택만 끝났으면 `선택 완료 · 제품 명세 미완료`로 보고하며, 이를 사전 준비 완료로 확대하지 않는다. 새 예제 업무·입력 후보를 임의 확정하거나 스타터 준비로 이 단계를 대체하지 않는다. 다음 command는 안내만 한다.

기존 ideation·선택 기록이 있으면 최신 사용자 결정과 대조해 현재 선택, 추가 탐색, 보류, 과거 기록을 구분한다. 재검토 요청만으로 새 방향이 선택됐다고 보거나 기존 선택을 덮어쓰지 않는다. 기록과 최신 결정이 충돌하고 의도가 불명확하면 선택 상태를 확인한다.

비교를 시작할 때 새 후보만 비교하는지, 기존 후보를 포함한 전체 후보를 비교하는지와 포함·제외 대상을 먼저 명시한다. 새 후보 내 순위를 전체 추천으로 확대하지 않는다. 추천이 바뀌면 이전 추천 대비 새로 확인한 근거와 판단의 차이를 설명한다. 비교 범위만 바뀐 경우도 구분하며 추천과 사용자 선택은 별도로 유지한다.

사용자가 이해하기 어렵다고 하면 후보를 더 늘리기보다 한 명의 사용자가 넣는 구체 입력 → 제품에서 하는 행동 → 받는 결과의 한 시나리오로 먼저 설명한다. 실제 검증 결과가 아닌 예시는 가정으로 표시한다.

## 절차

1. 공개된 공식 심사 기준이 있으면 평가 축으로 그대로 쓴다. 없으면 기준을 지어내지 않고 공식 행사 목표·참가 또는 수료 조건을 별도 축으로 사용하며, 실제 심사 기준은 미확인으로 표시한다.
2. 기존 제품부터 읽되 우선 채택하지 않는다. 새 공식 트랙·필수 기술·심사 기준으로 기존 아이디어 유지 / 수정 / 새 후보를 동등 비교한다. 기존 strategy의 prefer_existing_product도 재평가를 제한하지 않는다. 아이디어 적합성과 코드 재사용 자격은 별도 축이다.
3. 직접 참가한 과거 행사에서 반복된 실수와 유효했던 전략을 확인한다.
4. 관련 수상작의 구조를 확인한다.
5. 전체 출품작에서 이미 흔한 아이디어인지 확인한다.
6. sponsor별 requirement(없으면 행사 기본값)와 채택 후보를 확인해 각 제품의 핵심 실행 경로에 자연스럽게 들어갈 수 있는지 본다. 행사 기본값 `none`만으로 개별 요건이나 선택적 채택을 건너뛰지 않는다. fit이 없는 sponsor를 억지로 넣지 않는다.
7. demo를 제한 시간 안에 설명하고 재현할 수 있는지 본다.
8. 공식 행사 규칙과 사용자 승인 범위 안에서 사전 준비·구현 가능한 범위를 본다. 현장 제작만 허용되면 사전 구현 완료를 요구하지 않는다.
9. 새 규칙 재평가에서는 기존안이 맞더라도 새 후보와 비교한다. planning이 금지·미확인이면 새 아이디어 작성은 보류하고 기존 기록의 적합성·규칙 차이 등 비차단 검토를 수행한다. rules/출처 부족은 부분완료이며 허용 추론은 금지한다.

## 찾은 레퍼런스 기록

아이데이션 중 찾은 레퍼런스는 그 자리에서 kit `references/`에 남긴다. 수상작은 `winners.md`, 출품작 gallery는 `submissions.md`, 유사 제품·행사 형식·투표나 쇼케이스 경향은 `inspirations.md`다. 항목마다 URL, 확인 날짜, 확인 방법(직접 열람·Playwright 렌더·검색 요약), 한계, 어느 행사 아이데이션에서 찾았는지를 한 줄로 적는다. 막힌 페이지는 헤드리스 브라우저로 다시 시도하고, 끝내 못 열면 못 열었다고 적는다. 이 기록은 `/archive` 전이라도 남기며, 행사 결과나 우리 출품 링크는 계속 `/archive`가 맡는다.

선택지는 3개 이하로 줄인다. 각 선택지에는 아래를 적는다.

- 문제
- 어떤 사용자가 겪는가
- 문제 근거의 종류(관심 / 경험 / 과거 요구 / 실제 수요), 출처와 확인 범위. 관심이나 과거 요구를 현재 실제 수요로 확대하지 않으며, 코드에서 찾지 못했다는 이유만으로 운영에도 없다고 단정하지 않는다. 미확인 내용은 가설로 표시한다.
- 기존 해결 방식과 그 대비 차이. 유력 추천에는 가장 강한 반론과 추천을 철회할 조건을 함께 적는다.
- 심사 기준별 근거
- sponsor fit. 실제 해당하지 않을 때만 N/A. 미정·unknown은 확인 항목이며, `required`/`judged`인데 fit이 없으면 자격 또는 점수 손실
- demo 한 장면
- build_policy에 따른 허용된 제작 시점과 범위
- 현장에서 남을 작업
- 구현 리스크
- reference에서 확인한 유사점과 차이

사용자가 방향을 고르면 현재 행사 workspace의 `hackathon.yaml`에 선택한 제품 또는 아이디어를 기록한다. sponsor 채택 결정은 `AGENTS.md`의 Sponsor 사용 조건에 따라 `used: true/false/null`과 이유로 적는다. null·누락은 미정이지 제외나 N/A가 아니며, 채택은 실제 사용 evidence가 아니다. 제품 방향 선택을 실제 구현 승인으로 확대하지 않는다.

선택 확정과 함께 제품명을 결정하도록 유도한다. 종료 시 1~3개의 임시 제품명 안을 짧은 근거와 함께 제시하고 사용자가 하나를 고르게 한다. 사용자가 결정하면 `hackathon.yaml`의 `product.name`에 기록한다. 결정이 늦어지면 임시 코드명을 명시해 `product.name`에 넣고, 재명명 시 영향 범위(제품 저장소/화면/문서/덱/제출 폼 중 해당 항목)를 `ideation.md` 또는 `hackathon.yaml` notes에 기록해 이후 `/adapt`·`/retro`에서 추적한다. `AGENTS.md`의 저장소 이름 규칙(행사명+날짜)과 설명 규칙은 유지하고 과거 행사의 일괄 rename은 하지 않는다.

전체 재평가 결과는 `workspace/<event-slug>/ideation.md`에 이전 선택·근거를 보존하여 남긴다. 기존 선택은 `재평가 대기`로 명시하고 recommendation과 사용자 결정을 분리한다. 사용자 승인 없이 product·명칭·sponsor 채택을 덮어쓰지 않는다. `/replan` 내부에서는 이 조사·비교·기록·추천까지 실제 수행하고 선택 대기로 끝낸다.
